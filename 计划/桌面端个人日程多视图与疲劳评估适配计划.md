> 文档状态：讨论稿，供确认后实施  
> 更新日期：2026-08-10  
> 适用范围：Tauri 2 桌面端完整工作台、快捷小窗口（`quickTimeline` 模式）  
> 配套主计划：[个人日程紧急度与疲劳评估实现计划](./个人日程紧急度与疲劳评估实现计划.md)

## 一、文档关系与拆分决策

### 1.1 两份计划各自负责什么

本文件不是另一套疲劳算法，而是桌面端的适配和验收计划。两份文档的职责如下：

| 文档 | 负责内容 |
| --- | --- |
| [个人日程紧急度与疲劳评估实现计划](./个人日程紧急度与疲劳评估实现计划.md) | 产品口径、数据库字段、后端接口、负荷算法、调查模型、隐私和跨端共享契约 |
| 本文件 | Tauri 完整工作台、快捷小窗口、窗口生命周期、托盘、原生通知、桌面交互和桌面验收 |

若两份文档出现冲突，以主计划中的业务规则、字段含义、接口契约和权限规则为准；本文件只决定桌面端如何呈现和调用这些能力。桌面端不得复制一套独立的疲劳计算公式。

### 1.2 为什么拆成两批开发

本次内容同时涉及字段、四种视图、快捷窗口重构、每日汇总、日终调查、通知和 Tauri 生命周期。如果一次完成，容易出现以下问题：

- 小窗口继续把个人日程和团队任务混在一起，统计结果看似正常但业务口径错误。
- Web、完整桌面窗口和快捷小窗口的表单字段不一致，AI 草稿可能覆盖用户选择。
- 客户端用当前分页数据临时相加，漏掉已完成或其他页数据。
- 调查通知依赖隐藏窗口中的定时器，用户可能收不到或重复收到提醒。

因此采用两个有明确出口条件的开发批次：

1. **第一批：字段与四种查看方式同步。** 先让 Web 用户端、完整桌面工作台和快捷小窗口三个形态都能正确创建、编辑、展示和切换个人日程。
2. **第二批：疲劳摘要、调查与原生体验。** 在第一批数据隔离和视图契约稳定后，再接入负荷上限、日终调查、提醒和托盘联动。

只有完整工作台和快捷小窗口都完成四种个人日程视图，第一批才算完成；不能只改 Web 页面后把桌面计划标记为完成。

### 1.3 明确不纳入桌面分类的内容

- 团队任务不进入“时间、分组、紧急、疲劳”四种个人日程视图。
- 团队任务不进入个人日程数量、预计负荷、已完成负荷、疲劳提醒、日终调查训练数据或个人模型。
- 团队任务继续沿用接受、执行、完成、审批、取消等团队任务规则。
- “桌面端同步”第一版指业务数据和功能同步，不代表 Web 与桌面共享查看模式的本地偏好。若未来需要跨端同步偏好，另增用户偏好接口。

## 二、当前桌面端基线

### 2.1 技术和复用关系

当前桌面端采用 Tauri 2 + Vue 3 + TypeScript + Vite + Pinia。完整工作台通过 `@web` 别名直接复用用户端代码：

| 桌面入口 | 实际复用内容 | 适配结论 |
| --- | --- | --- |
| `src/desktop/vite.config.ts` | `@web` 指向 `src/web-user/src` | 类型、API、store、工具和样式应优先共享 |
| `src/desktop/src/router/index.ts` | `/schedules` 使用 `@web/views/SchedulesPage.vue` | Web 日程页改造后，完整桌面窗口自然获得同一能力 |
| `src/desktop/src/views/DesktopLayout.vue` | 完整导航、通知轮询、快捷模式入口 | 只补桌面专属行为，不复制日程业务规则 |
| `src/desktop/src/stores/desktopShell.ts` | 窗口尺寸、置顶、透明度、托盘通知开关 | 不把日程排序和疲劳模型塞进窗口设置 store |
| `src/desktop/src/components/DesktopQuickTimeline.vue` | 快捷小窗口的独立时间轴和视图栈 | 需要单独重构，是本计划的主要桌面工作量 |
| `src/desktop/src/components/DesktopQuickScheduleEditor.vue` | 快捷窗口创建/编辑个人日程 | 需要增加紧急度和疲劳度五档控件 |
| `src/desktop/src/services/native.ts` | Tauri 窗口尺寸、原生通知权限和发送 | 第二批补通知导航、生命周期和窗口约束 |
| `src/desktop/src-tauri/src/lib.rs` | 系统托盘与关闭到托盘 | 第二批按需增加调查入口和通知动作 |

### 2.2 快捷小窗口的真实形态

快捷小窗口不是第二个 Tauri 窗口，而是同一主窗口切换 `quickTimeline` 布局并调整尺寸：

- 默认尺寸约 `468 × 760`。
- 最小尺寸约 `420 × 600`。
- 完整工作台最小尺寸约 `1024 × 680`。
- `src/desktop/src/services/native.ts` 会保存完整工作台尺寸和最大化状态，切换回来时恢复。
- `src/desktop/src/views/DesktopLayout.vue` 在快捷模式下只渲染 `DesktopQuickTimeline`，隐藏完整导航和路由页面。

这意味着“通知点击打开调查”不能假设存在独立小窗句柄，必须通过 `desktopShell` 的目标状态和现有视图栈完成导航。

### 2.3 当前实现造成的风险

`DesktopQuickTimeline.vue` 当前把个人日程和团队任务合并到 `allItems`、`entries`、`overdueEntries`、`timelineEntries`、`unscheduledEntries` 和 `stats` 中，并通过 `fetchAllPages(size=100)` 循环抓取待处理分页。直接在末端加排序会同时污染标题数量、空状态和负荷汇总。

当前通知行为还存在以下限制：

- `DesktopLayout.vue` 每 45 秒轮询未读通知并调用 `sendNativeNotification`。
- 窗口隐藏到托盘后，WebView 定时器可能降频，不能依靠前端计时器判断日终调查是否到点。
- 原生通知没有点击后导航到调查视图的处理。
- 托盘菜单目前主要是“打开”和“退出”，没有待调查入口。
- 快捷模式仍可能允许最大化，窄窗口布局会失去定位。

这些现状必须在实现时显式处理，而不是当作普通 CSS 调整。

### 2.4 当前版本 `.exe` 保留规则

用户已要求保留当前版本的 `.exe`。后续桌面开发和打包必须遵守：

1. 不覆盖项目根目录或现有发布目录中的 `Dayliane-timeline.exe` 及其他当前版本启动程序。
2. 构建产物输出到独立目录，例如 `发布包/desktop/<版本号>/` 或 `dist/desktop/<版本号>/`。
3. 发布目录使用版本号、提交号或时间戳区分，保留构建日志、校验和与构建配置快照。
4. 在 Windows 实机验证新包后，再由用户决定是否替换默认启动入口。
5. 回滚只需重新指向旧版本目录，不删除旧 `.exe` 和其依赖文件。

## 三、共享业务契约（桌面必须遵守）

### 3.1 字段和枚举

桌面端直接复用主计划的类型和接口，建议在共享类型中固定以下名称：

| 契约 | 值 | 说明 |
| --- | --- | --- |
| `ScheduleLevel` | `1 / 2 / 3 / 4 / 5` | 紧急程度和预计疲劳程度均使用五档 |
| `ScheduleViewMode` | `time / group / urgency / fatigue` | 个人日程四种查看方式 |
| `ScheduleSource` | `schedule / team_task` | 明确数据来源，禁止隐式混合 |
| 疲劳系数 | `1 / 2 / 3 / 5 / 8` | 五档初始系数，数字越大代表预计负荷越高 |

推荐默认值：紧急程度为 `3`，预计疲劳程度为 `3`。数字越大越紧急、越疲劳；紧急度和疲劳度是独立字段。

### 3.2 统一的排序、分区和状态规则

- 时间模式按日期归属、逾期、开始时间、截止时间和稳定 ID 排序。
- 分组模式按个人分组折叠；未分组单独放入“未分组”。
- 紧急模式按 `5 → 1` 分区，同级再按逾期、时间和稳定 ID 排序。
- 疲劳模式按 `5 → 1` 分区，同级再按紧急度、逾期、时间和稳定 ID 排序。
- 分区 key、显示标签、`sectionSummaries`、`dataRevision` 与 Web 完全一致。
- 已完成日程的完成快照由后端保存；已完成任务不允许直接取消。恢复、编辑和其他状态变更沿用主计划的状态机。
- 服务端返回的 `localDate`、用户时区、计划负荷和实际负荷是事实来源，桌面不使用 Windows 本地日期自行推断。

### 3.3 团队任务隔离不变量

以下断言必须在后端、共享工具、Web 和桌面测试中同时成立：

```text
team_task 不进入个人四种视图
team_task 不进入个人 sectionSummaries
team_task 不进入 plannedLoad / completedLoad / predictedScore
team_task 不进入 topContributors
team_task 不进入疲劳调查训练和个性化模型
```

不能先把两种来源合并后再在模板中隐藏团队任务；数据管线、统计和空状态都必须在源头分开。

## 四、完整桌面工作台适配

### 4.1 页面范围

由于完整工作台复用 Web 页面，第一批不新建一套桌面日程页，而是保证以下共享页面完成桌面验证：

- `src/web-user/src/views/SchedulesPage.vue`：四种个人日程查看模式、等级筛选和个人统计。
- `src/web-user/src/views/ScheduleDetailPage.vue`：等级、系数快照、状态和编辑入口。
- `src/web-user/src/views/HomePage.vue`：今日个人负荷摘要，明确排除团队任务。
- `src/web-user/src/views/NotificationsPage.vue`：疲劳提醒和待调查入口。
- `src/web-user/src/views/NotificationSettingsPage.vue`：桌面原生通知和安静时段偏好。

桌面端路由只需补充调查目标的导航协议和快捷模式恢复逻辑，不复制这些页面的业务判断。

### 4.2 桌面工作台的交互要求

- 完整窗口 `/schedules` 必须显示“时间、分组、紧急、疲劳”切换控件。
- 创建、编辑和 AI 草稿确认都能设置两个五档字段，默认值和校验与 Web 相同。
- 卡片使用图标、数字和文字同时表达等级，不能只依赖颜色。
- 完成后的日程仍可查看完成时的疲劳系数快照；已完成日程不可直接取消。
- 视图切换后保留筛选、展开状态和滚动位置；用户切换账号后不得继承上一账号的模式。
- 桌面窗口在 `1024 × 680` 最小尺寸下无横向溢出，长标题、分组名和等级标签可换行。

### 4.3 完整窗口和 Web 的状态关系

共享页面可以共用 `dayliane_schedule_view_<userId>` 作为 Web/完整工作台的本地模式 key。快捷小窗口必须使用独立 key，避免窄窗口的模式偏好覆盖完整工作台：

```text
dayliane_schedule_view_<userId>
dayliane_desktop_quick_schedule_view_<userId>
```

本地偏好只负责呈现，不替代服务器保存的日程或疲劳数据。退出登录时清理内存状态，并校验新用户的 key。

## 五、快捷小窗口信息架构

### 5.1 顶层来源切换

快捷窗口顶部按以下顺序组织：

```text
个人日程 | 团队任务
```

默认进入“个人日程”。来源切换与查看模式切换是两个层级：只有选择个人日程时才显示四段查看控件；选择团队任务后隐藏四段控件，避免用户误以为团队任务也支持个人疲劳分类。

建议的数据结构：

```ts
type QuickTimelineData = {
  personalEntries: QuickScheduleEntry[]
  teamEntries: QuickTeamTaskEntry[]
  personalSections: ScheduleSection[]
  teamTimeline: QuickTeamTaskEntry[]
  fatigueSummary: FatigueSummary | null
  pendingSurvey: PendingFatigueSurvey | null
  revision: string
}
```

### 5.2 个人日程快捷范围

为保持启动速度和窄窗口可读性，第一版快捷范围建议为：

- 逾期的未完成个人日程。
- 今天归属的未完成个人日程。
- 今天尚未安排时间的个人日程。

完整工作台仍负责全部未来日程、历史记录和复杂筛选。快捷窗口每个分区先显示有限条目，并提供“查看全部”跳转完整工作台；不能继续无限循环抓取所有分页。

若产品最终要求快捷窗口显示未来全部日程，应改为服务端分页和“加载更多”，不能恢复客户端 `fetchAllPages(size=100)` 的方案。

### 5.3 四种个人模式

| 模式 | 主要内容 | 次级排序 | 窄窗交互 |
| --- | --- | --- | --- |
| 时间 | 逾期、今日时间轴、未安排 | 开始时间、截止时间、稳定 ID | 保留时间指针和倒计时 |
| 分组 | 个人分组折叠列表 | 组内紧急度、时间 | 只查看和折叠，不在窄窗拖拽管理分组 |
| 紧急 | `5 → 1` 五档分区 | 逾期、时间、稳定 ID | 显示分区数量和预计负荷 |
| 疲劳 | `5 → 1` 五档分区 | 紧急度、逾期、时间 | 显示档位系数和负荷摘要入口 |

切换模式时：

- 保留当前状态筛选和日期范围。
- 为每个模式分别记忆滚动位置。
- 使用请求序号或 `AbortController`，旧请求返回后不得覆盖新模式。
- 空状态文案必须区分“该模式无个人日程”和“网络加载失败”。
- 切换控件在 `420px` 最小宽度下保持单行等宽；必要时只使用短标签和图标，长解释放到 tooltip 或详情。

### 5.4 团队任务独立区域

选择“团队任务”后继续使用现有团队任务时间线和操作：接受、完成、查看详情、审批或其他既有动作。团队任务卡片：

- 不显示个人紧急度、预计疲劳度和疲劳系数。
- 不使用个人负荷颜色或个人疲劳提醒。
- 统计只显示团队任务自身数量和状态，不污染个人摘要。
- 若团队任务需要紧急程度，另行设计团队任务字段，不能复用个人日程字段。

## 六、创建、编辑、详情和 AI 草稿

### 6.1 快捷创建与编辑

`src/desktop/src/components/DesktopQuickScheduleEditor.vue` 增加两个五档数字选择器：

```text
紧急程度  1  2  3  4  5
预计疲劳  1  2  3  4  5
```

要求：

- 两行控件各自独立，默认选择 3。
- 五个按钮等宽，选中态同时提供数字、短文字和可访问名称。
- 键盘、鼠标和触摸均可操作；焦点顺序符合表单顺序。
- 只接受整数 1～5；前端校验用于友好提示，后端校验才是最终约束。
- 编辑已有日程时回填服务端值；旧数据为空时按默认 3 展示并在保存时补齐。
- 创建、编辑成功后刷新快捷列表、分区数量和相关负荷摘要。

### 6.2 详情和完成状态

个人日程详情至少展示：

- 紧急程度及文字标签。
- 预计疲劳程度及当前系数。
- 若已完成，显示完成时的疲劳等级和系数快照。
- 当前状态、归属日期、分组和提醒信息。

已完成日程不可直接取消。若允许恢复为待完成，必须沿用主计划规定的状态机，并明确恢复后是否允许再次取消；桌面端不能单独放宽规则。

### 6.3 AI 创建和编辑草稿

AI 解析只负责填充可解析的标题、描述、时间和分组等草稿字段：

- 不根据标题擅自决定疲劳等级。
- 用户已有的紧急度和疲劳度选择不能被 AI 覆盖。
- 新建草稿缺少等级时使用默认 3，并在提交前明确显示两个选择器。
- AI 子任务保存期间，窗口切换到完整工作台或调查视图需要经过现有退出保护。
- AI 解析失败不能阻止用户手动保存，也不能产生半保存日程。

### 6.4 共享 payload 清单

第一批接入时逐项核对，避免只改了模板：

```text
Schedule 类型
ScheduleForm 类型
新建表单默认值
编辑表单回填
创建 payload
编辑 payload
详情转换器
列表卡片转换器
AI 草稿标准化
缓存/乐观更新
```

## 七、桌面负荷摘要与疲劳呈现

### 7.1 第一批的基础摘要

第一批可以先展示后端返回的基础统计，不启用个性化学习：

- 今日个人日程预计负荷。
- 今日已完成个人日程负荷。
- 预计贡献最大的个人日程。
- 当前默认承受上限及提醒档位（若后端已提供）。

摘要必须来自后端汇总接口或主计划定义的 `sectionSummaries`，不能从当前快捷窗口已加载的几条记录临时相加。原因是快捷列表可能只含待办，已完成快照和其他分页数据不能丢失。

### 7.2 第二批的完整负荷状态

第二批接入以下字段并保持和 Web 一致：

```text
plannedLoad
completedLoad
predictedScore
personalCapacity
alertLevel
modelStage
algorithmVersion
topContributors
```

快捷窗口头部使用紧凑摘要，点击后进入负荷明细视图；完整工作台显示可解释的详细来源。所有数字都标注“预计”“已完成”或“用户反馈”，不把预测分数写成医疗结论。

### 7.3 日程变更后的刷新

创建、编辑、完成、恢复、取消或日期变更后：

1. 先以服务端响应更新当前卡片。
2. 重新请求受影响日期的个人分区和疲劳摘要。
3. 若存在待调查，更新调查状态但不强行覆盖正在编辑的视图。
4. 失败时保留原数据并显示可重试提示，不能因为摘要刷新失败而回滚已经成功保存的日程。

## 八、日终调查、提醒和原生通知

### 8.1 调查入口

建议新增桌面专用组件 `DesktopQuickFatigueSurvey.vue`，并把调查作为快捷窗口内部视图栈的一种类型，而不是浏览器弹窗：

```ts
type QuickView =
  | { kind: 'timeline'; scrollTop: number }
  | { kind: 'schedule-create'; scrollTop: number }
  | { kind: 'schedule-edit'; id: number; scrollTop: number }
  | { kind: 'team-create'; scrollTop: number }
  | { kind: 'team-edit'; id: number; scrollTop: number }
  | { kind: 'schedule-detail'; id: number; scrollTop: number }
  | { kind: 'fatigue-survey'; localDate: string; scrollTop: number }
```

调查视图包含：

- 0～100 滑块，提供 `0/25/50/75/100` 锚点和当前数值。
- 今日完成负荷、系统预测分数和模型阶段。
- “存在额外影响”开关及可选原因。
- `提交`、`稍后提醒`、`今天跳过`三个明确动作。
- 草稿本地暂存；提交成功后删除草稿，失败时保留并允许重试。

调查到期时先显示非阻塞横幅。若用户正在编辑日程、保存 AI 子任务或有未保存内容，只记录 `pendingQuickTarget`，待当前操作安全结束后再进入调查。

### 8.2 调查时间和幂等

- 后端按用户资料时区决定调查日期和触发窗口。
- 桌面使用接口返回的 `localDate`，不使用 Windows 本地日期覆盖它。
- 应用启动、窗口从托盘恢复、页面重新可见、跨日和网络恢复时都检查待调查。
- 同一用户同一日期只能提交一次；重复点击、重复轮询和多端提交应得到幂等响应。
- “跳过”和“稍后提醒”要区分：跳过记录用户决定，稍后提醒只改变下一次提醒时间。

### 8.3 疲劳提醒和通知导航

后端产生 `fatigue_warning`、`fatigue_survey` 等通知类型，桌面轮询只负责获取和展示：

- 原生通知、站内通知和快捷窗口横幅使用同一通知 ID 去重。
- 通知响应携带 `type`、`localDate`、`targetRoute` 或等价导航元数据。
- 点击调查通知后显示主窗口，切换快捷模式，并打开调查视图；若无法直接接收原生点击事件，至少保证重新打开窗口后出现待调查入口。
- 原生通知未授权时保留站内横幅，不阻止日程保存。
- 通知失败不影响后端已保存的负荷和调查数据。

### 8.4 托盘菜单

第二批为托盘增加动态菜单项：

- 打开工作台。
- 查看快捷时间轴。
- 填写今日日终调查（仅在存在 `pendingSurvey` 时显示或启用）。
- 退出。

Rust 端负责显示窗口、聚焦窗口和传递导航意图；Vue 端负责具体路由和视图栈。不要把业务计算放入 Rust。

## 九、窗口生命周期、后台和异常处理

### 9.1 窗口尺寸和最大化

- 快捷模式验证 `420 × 600` 和 `468 × 760` 两个尺寸。
- 完整工作台验证 `1024 × 680` 和常用桌面尺寸 `1280 × 800`。
- 快捷模式默认禁止最大化，或在最大化前自动退出快捷模式并恢复完整工作台尺寸。
- 从快捷模式返回时恢复进入前的完整窗口尺寸和最大化状态。
- Windows 缩放 100%、125%、150% 下四段切换、五档控件和滑块不能横向溢出。

### 9.2 可见性、托盘和刷新

- 页面可见时按现有 45 秒轮询通知，但轮询是补偿机制，不是疲劳规则的唯一计时器。
- 从托盘恢复、窗口重新可见、登录用户切换和跨日时立即刷新个人分区、负荷摘要和待调查状态。
- 快捷模式只刷新当前日期和服务端返回的摘要，避免后台无限加载历史页。
- 网络错误保留最近一次成功数据，显示离线或待同步标识；恢复网络后使用 `revision` 或 ETag 重新校验。
- 任何异步请求都要带用户 ID、日期和模式上下文，避免退出登录后旧响应写入新账号。

### 9.3 请求竞态和分页

建议桌面概览接口一次返回：

```json
{
  "personalSections": [],
  "teamTasks": [],
  "fatigueSummary": null,
  "pendingSurvey": null,
  "revision": "..."
}
```

若暂时不能新增接口：

- 个人日程和团队任务必须分开请求。
- 每种模式使用服务端排序和分页。
- 使用请求序号或 `AbortController` 取消旧请求。
- 不使用 `fetchAllPages(size=100)` 计算个人统计。
- “查看全部”跳转完整工作台，而不是在小窗口一次渲染整个历史。

## 十一、两批实施顺序

### 11.1 第一批：字段与四种查看方式同步

**目标：** 三个形态（Web 用户端、完整桌面工作台、快捷小窗口）使用同一字段、排序和团队隔离规则。

实施顺序：

1. 冻结主计划中的字段、枚举、默认值、状态机和 API 响应契约。
2. 完成数据库迁移、后端校验、列表/详情/分区统计及团队隔离测试。
3. 提取共享类型、标签、排序和分区纯函数。
4. 完成 Web 日程页、详情页、首页摘要和 AI 草稿字段。
5. 验证完整桌面工作台复用 Web 改造，不出现独立分支逻辑。
6. 重构快捷小窗口为 `personalEntries` / `teamEntries` 两条管线。
7. 在快捷小窗口实现来源切换和四种个人模式，补分页、模式记忆和请求竞态处理。
8. 补快捷创建、编辑、详情、AI 草稿确认中的两个五档字段。
9. 在 `420 × 600`、`468 × 760`、`1024 × 680` 和 `1280 × 800` 下完成视觉与交互验收。

第一批不做个性化系数学习，但可以展示后端已经提供的基础负荷摘要。

**第一批出口条件：**

- 三个形态均能创建和编辑紧急度、预计疲劳度 1～5。
- 快捷小窗口四种个人模式均可切换、刷新和恢复偏好。
- 团队任务在四种个人视图、个人统计和任何负荷结果中均为 0 贡献。
- 已完成个人日程不能取消，完成快照可查看。
- 快捷模式不再依赖客户端全量抓取计算统计。

### 11.2 第二批：疲劳累计、调查与桌面原生体验

**目标：** 桌面端完整呈现主计划中的每日负荷和调查闭环，并与托盘、原生通知协同。

实施顺序：

1. 完成 `fatigueSummary`、个人 profile、每日汇总、调查和 preview 等共享后端接口。
2. 完成 Web 今日负荷、调查、模型状态和通知设置。
3. 完整桌面工作台同步负荷明细、调查入口和站内提醒。
4. 快捷窗口增加负荷条、临界提醒、调查 `QuickView`、草稿暂存和返回滚动位置。
5. 原生通知支持疲劳提醒和调查通知，补通知 ID、导航元数据和点击跳转。
6. 托盘增加待调查菜单项，处理隐藏、恢复、跨日、网络恢复和安静时段。
7. 增加功能开关、模型回滚和逐用户灰度发布。

**第二批出口条件：**

- Web、完整桌面和快捷小窗口对同一天返回相同的 `plannedLoad`、`completedLoad` 和 `predictedScore`。
- 调查按用户时区每日最多一次，提交、跳过和稍后提醒幂等。
- 原生通知、站内通知和横幅不重复轰炸。
- 窗口隐藏、恢复和重启后仍能找到待调查入口。
- 调查不会打断未保存的日程或 AI 操作。

## 十二、测试矩阵与验收门禁

### 12.1 契约门禁

- 数据库迁移、默认值、1～5 校验和 completed 快照测试通过。
- API 返回统一字段、`localDate`、`sectionSummaries`、`dataRevision` 和疲劳摘要。
- 团队任务隔离测试覆盖列表、分区、统计、调查和模型训练。
- 后端分页和排序在同一稳定 ID 下结果可重复。

### 12.2 完整工作台门禁

- `/schedules` 可在四种模式间切换，刷新后分区和排序不漂移。
- 创建、编辑、详情、AI 草稿和完成状态都能读写两个等级。
- 个人统计不含团队任务；已完成任务不能取消。
- `1024 × 680` 下无横向溢出、遮挡或按钮跳动。

### 12.3 快捷小窗口门禁

- 顶层来源切换可用；个人来源才显示四段控件。
- 四种模式均只显示个人日程，团队任务始终在独立区域。
- 快速连续切换模式不会被旧响应覆盖。
- 分区支持有限渲染和“查看全部”，不无限加载历史分页。
- `420 × 600`、`468 × 760` 以及 Windows 缩放 100/125/150% 下无横向滚动和文字重叠。
- 模式和滚动位置按用户隔离；A 用户退出后，B 用户不能继承 A 的本地状态。

### 12.4 疲劳和通知门禁

- 完成个人日程后摘要刷新，完成快照不丢失。
- 日终调查滑块只能提交 0～100；同一天重复提交幂等。
- 调查待办在启动、托盘恢复、重新可见和跨日后可见。
- 原生通知未授权时站内提醒仍可用；已授权时不重复展示同一通知。
- 通知点击或托盘入口能进入调查，且不会覆盖未保存编辑。

### 12.5 构建回归门禁

按仓库实际脚本执行并记录结果：

```text
npm test
npm run build
npm run tauri:build
cargo test
cargo check
```

如果某个脚本名称不存在，记录实际替代命令和未执行原因；至少完成 TypeScript 类型检查、Web 构建、桌面构建和 Rust 检查。Tauri Windows 实机需要额外验证托盘、置顶、隐藏到托盘、快捷切换、通知权限和窗口尺寸。

## 十三、发布、版本保留与回滚

### 13.1 构建产物

建议约定如下目录，不直接写入根目录：

```text
发布包/
  desktop/
    <版本号或提交号>/

      *.msi
      build-info.json
      checksums.txt
      logs/
```

`build-info.json` 至少记录构建时间、提交号、前端版本、后端 API 版本和功能开关。构建脚本若默认输出到 `src-tauri/target/release`，发布复制步骤也必须使用带版本号的目标目录。

### 13.2 回滚策略

- 旧版 `.exe` 和依赖文件保持原位，不做覆盖式清理。
- 新版只在测试目录运行，通过 Windows 实机验收后再登记为候选版本。
- 疲劳模型或通知异常时，可关闭第二批功能开关，保留第一批四视图和等级字段。
- 回滚应用版本不删除新增数据库字段；旧代码忽略新字段即可继续运行。
- 日志统一放在发布目录下的 `logs/`，不把临时日志散落到项目根目录。

## 十四、实现前需要确认的桌面口径

主计划中的产品口径仍需优先确认，本文件额外列出桌面侧问题：

1. 快捷小窗口是否只展示“逾期 + 今天 + 未安排”，还是允许加载全部未来日程。
2. 快捷模式默认是否禁止最大化，或允许最大化时自动退出快捷模式。
3. Web 与桌面查看模式是否保持各自本地记忆，还是未来增加跨端同步偏好接口。
4. 调查通知点击是否要求第一版直接打开调查，还是先保证重启/恢复窗口后出现调查入口。
5. 托盘菜单中的“填写今日日终调查”是否在无待调查时隐藏，还是保留为禁用项。
6. 快捷窗口是否允许显示历史已完成日程；若允许，仍不得把团队任务计入个人统计。
7. 发布目录最终使用 `发布包/desktop` 还是现有构建目录下的版本化子目录。

推荐默认值：快捷窗口只展示逾期、今天和未安排的个人日程；快捷模式禁止最大化；两端模式偏好先分开记忆；第二批完成原生通知点击跳转；托盘无待调查时隐藏调查菜单项。
