## 一、方案目标

本方案是在现有个人日程能力上增加四类能力：

1. 用户创建或编辑个人日程时，可以选择 1～5 级紧急程度。
2. 用户创建或编辑个人日程时，可以选择 1～5 级预计疲劳程度。
3. 个人日程列表可以按时间、分组、紧急程度和疲劳程度切换查看。
4. 系统根据个人日程累计负荷、日终 0～100 疲劳调查和历史反馈，逐渐学习用户自己的每日疲劳承受上限。

方案需要同时满足以下原则：

- 紧急程度和疲劳程度是两个独立维度，不能互相代替。
- 疲劳等级由用户自己选择，系统不擅自判断任务一定有多累。
- 第一版使用简单、可解释的确定性规则，不使用外部 AI 计算疲劳。
- 计划负荷只能表述为“预计”，不能断言用户已经疲劳。
- 实际疲劳必须以用户日终调查为主要依据。
- 提醒只提供建议，不禁止用户创建或调整日程。
- 团队任务继续使用原有团队任务页面和规则，不混入个人疲劳模型。

## 二、当前项目现状与改造边界

### 2.1 当前后端现状

- `schedule` 表目前包含标题、描述、个人分组、时间类型、开始时间、结束时间、截止时间、状态和手动排序等字段。
- 当前没有 `urgency_level`、`fatigue_level`、`completed_at` 等字段。
- `ScheduleService` 使用 `Map<String, Object>` 和 SQL 直接完成创建、编辑、列表、详情和状态切换，没有独立日程 DTO。
- 创建接口固定创建为 `pending` 状态。
- 日程状态目前包括 `pending`、`completed`、`cancelled`。
- 当前首页“今日个人日程”主要读取待完成数据，如果直接复用该结果计算疲劳，任务完成后全天负荷会错误下降。
- 现有 `reminder` 机制面向某个具体任务的时间提醒，不适合直接承担每日累计疲劳提醒。
- 现有 `notification` 表和浏览器通知能力可以复用，但需要增加疲劳提醒和疲劳调查对应的通知类型与偏好。

### 2.2 当前用户端现状

- `SchedulesPage.vue` 已经支持个人分组、折叠、筛选、状态切换、跨分组移动和手动排序。
- 当前列表只按照个人分组组织，没有时间、紧急程度和疲劳程度四种统一查看模式。
- `ScheduleForm`、Pinia store、TypeScript 类型和时间转换工具均未包含紧急程度与疲劳程度。

### 2.3 明确边界

- 本方案的四种查看模式只处理 `schedule` 表中的个人日程。
- `team_task`、`team_task_assignee` 等团队任务数据不加入个人日程分区。
- 团队任务不参与个人预计负荷、实际负荷、日终调查训练和个性化上限计算。
- 如果首页或日历同时显示个人日程和团队任务，必须分成独立区域或通过 `sourceType` 明确区分。
- 管理员默认不能查看用户的日终疲劳调查、异常原因或个性化承受能力明细。

## 三、核心概念与字段口径

### 3.1 紧急程度

紧急程度用于回答“这件事应该多早处理”，只影响展示、排序和提醒解释，不参与疲劳系数计算。

| 等级 | 展示名称 | 建议语义 |
| --- | --- | --- |
| 1 | 不紧急 | 暂时没有明确时间压力 |
| 2 | 较低 | 可以延后处理 |
| 3 | 普通 | 按正常计划完成 |
| 4 | 紧急 | 应优先安排 |
| 5 | 非常紧急 | 临近硬截止或当天必须处理 |

统一规定：**数字越大越紧急，5 最高，1 最低。**

规则：

- 新建日程默认值为 3。
- 用户可以在创建、编辑和 AI 草稿确认时修改。
- 紧急程度与现有 `sortOrder` 分开保存。
- `sortOrder` 继续表示用户在“按分组”模式中的手动拖拽顺序。
- 系统可以在临近截止但紧急程度较低时提示检查，不能自动修改用户设置。

### 3.2 预计疲劳程度

界面字段建议使用“预计疲劳程度”或“预计精力消耗”，强调这是用户自己的事前判断，而不是医学诊断。

| 等级 | 展示名称 | 初始系数 |
| --- | --- | ---: |
| 1 | 几乎不累 | 1 |
| 2 | 轻微消耗 | 2 |
| 3 | 一般 | 3 |
| 4 | 比较劳累 | 5 |
| 5 | 非常劳累 | 8 |

统一规定：**数字越大，预计疲劳越高。**

使用非线性系数的原因：等级 5 对用户的影响通常不只是等级 1 的五倍，高强度任务应更明显地占用每日承受能力。

第一版规则：

- 新建日程默认值为 3，但界面必须明显展示，让用户可以一键修改。
- 疲劳等级由用户主动选择。
- 第一版不把紧急程度乘入疲劳系数。
- 第一版不强制引入预计耗时乘数，避免系统公式覆盖用户的主观判断。
- 预计耗时、时间冲突惩罚和实际投入时间可以作为后续增强，不作为第一版上线前置条件。

### 3.3 计划负荷、实际负荷和调查分数

三个指标必须分开：

```text
计划负荷：当天所有未取消、未删除个人日程的疲劳系数总和
实际任务负荷：当天完成的个人日程在完成时保存的疲劳系数总和
实际疲劳分数：用户在日终调查中填写的 0～100 分
```

计划负荷用于创建和调整日程时的事前提醒。

实际任务负荷用于和用户日终反馈建立个性化关系。

实际疲劳分数是用户的主观真实反馈，系统不能用计划负荷代替它。

## 四、日程日期归属与状态规则

### 4.1 日程归属日期

所有日统计都按照用户 IANA 时区计算，例如 `Asia/Shanghai`。数据库继续存 UTC 时间。

第一版采用以下归属规则：

- `point_event`：归属开始时间所在的本地日期。
- `deadline_task`：归属截止时间所在的本地日期。
- `duration_task`：第一版归属开始时间所在的本地日期。
- 没有可用时间的历史异常数据：归入“未安排时间”，不参与某一天的疲劳提醒。

跨多天持续任务在第一版只计入开始日期，避免同一条日程被重复累计。后续如增加预计投入时间，可以再按每天实际占用或预计投入进行拆分。

### 4.2 状态与负荷

| 状态 | 进入计划负荷 | 进入实际任务负荷 |
| --- | --- | --- |
| pending | 是 | 否 |
| completed | 是，保留在原计划日期 | 是，计入完成日期 |
| cancelled | 否 | 否 |
| deleted | 否 | 否 |

完成任务后，全天计划负荷不能突然降低。它只是从“待完成”移动到“已完成”，仍然代表当天已经安排并消耗过的任务。

### 4.3 完成快照

日程完成时保存：

- `completed_at`：完成操作的 UTC 时间。
- `completed_fatigue_level`：完成时的疲劳档位快照。
- `completed_fatigue_weight`：完成时使用的个性化系数快照。

这样后续个性化系数发生变化时，不会悄悄修改历史实际任务负荷。

如果允许将已完成任务恢复为待完成：

- 清空本次完成时间与完成系数快照。
- 重算完成日期的实际任务负荷。
- 如果该日期调查已经参与模型训练，应把该调查标记为数据已变化，并重新校准个性化模型。

当前项目中已完成日程不能直接取消，但可以先恢复为待完成再取消。实施时需要再次确认是否要彻底禁止这条绕行路径。

### 4.4 编辑和删除后的重算

以下变化必须重算受影响日期：

- 修改时间类型、开始时间、结束时间或截止时间。
- 修改疲劳程度。
- 完成、恢复、取消或恢复取消。
- 删除或管理员修改日程状态。
- 用户修改时区。

重算必须幂等，同一请求重试不能生成重复提醒。

## 五、四种个人日程查看模式

### 5.1 页面切换控件

个人日程页面顶部增加分段切换：

```text
时间 | 分组 | 紧急 | 疲劳
```

规则：

- 默认使用“时间”。
- 通过路由查询参数保存当前模式，例如 `?view=time`，同时用带用户 ID 的本地存储键 `dayliane_schedule_view_<userId>` 作为下次进入的默认值。
- 切换模式只改变展示和排序，不修改任何日程数据。
- 搜索、状态、日期范围筛选继续对四种模式生效。
- 团队任务不进入任何一个分区。
- 非“分组”模式隐藏拖拽排序和上下移动按钮，避免用户误以为拖拽会改变时间、紧急或疲劳等级。

### 5.2 按时间查看

建议分区：

1. 已逾期或已错过
2. 今天
3. 明天
4. 本周
5. 以后
6. 未安排时间
7. 已完成（默认折叠）

排序规则：

- `deadline_task` 截止时间已过且仍未完成时标记“已逾期”。
- `duration_task` 结束时间已过且仍未完成时可以标记“已逾期”。
- `point_event` 发生时间已过但未完成时标记“已错过”，不能错误描述成截止任务逾期。
- 已逾期或已错过的未完成日程始终置顶，并保持两种文案可区分。
- 其余按有效时间从近到远。
- 有效时间：截止任务使用截止时间，持续任务和时间点事件使用开始时间。
- 同一时间使用紧急程度从高到低，再使用 ID 保证稳定排序。

日期分区标题可显示：

```text
8月12日 · 6项个人日程 · 预计负荷 17 / 个性化上限 20
```

### 5.3 按分组查看

继续复用现有个人任务分组：

- 按 `task_group.sort_order` 展示。
- 未匹配有效分组的日程进入“未分组”。
- 已完成日程保留独立折叠区。
- 分组内首先显示逾期任务，其次沿用用户手动 `sortOrder`。
- 仅该模式支持分组拖拽、跨分组移动和手动排序。
- 删除分组不删除日程，日程移动至合法默认组或“未分组”。

### 5.4 按紧急程度查看

分区顺序：

```text
5 非常紧急
4 紧急
3 普通
2 较低
1 不紧急
```

同一档内排序：

1. 逾期未完成优先。
2. 有效时间从近到远。
3. 疲劳程度从高到低。
4. ID 保证稳定顺序。

### 5.5 按疲劳程度查看

分区顺序：

```text
5 非常劳累
4 比较劳累
3 一般
2 轻微消耗
1 几乎不累
```

同一档内排序：

1. 紧急程度从高到低。
2. 有效时间从近到远。
3. ID 保证稳定顺序。

任务卡片同时显示用户选择和当前系数，例如：

```text
预计疲劳：4 比较劳累 · 当前系数 5
```

### 5.6 分页与分区统计

不能只拿前端当前页的 12 条日程计算完整分区数量和疲劳合计。

建议扩展 `GET /api/v1/schedules`：

```text
viewMode=time|group|urgency|fatigue
urgencyLevel=1..5
fatigueLevel=1..5
```

响应除现有分页字段外增加：

```json
{
  "viewMode": "urgency",
  "sectionSummaries": [
    {
      "key": "urgency:5",
      "label": "非常紧急",
      "total": 4,
      "pendingCount": 3,
      "plannedLoad": 21
    }
  ]
}
```

后端负责完整过滤集的分区统计和稳定排序，前端只负责展示当前页数据。以后如果单个分区数据很多，再增加分区级懒加载；第一版不使用“把 pageSize 调到很大”替代正确统计。

## 六、每日疲劳负荷计算

### 6.1 初始系数

所有用户初始使用：

```text
等级1 = 1
等级2 = 2
等级3 = 3
等级4 = 5
等级5 = 8
```

示例：用户当天有等级 2、3、5 的三项个人日程：

```text
计划负荷 = 2 + 3 + 8 = 13
```

### 6.2 默认个人承受上限

在没有足够调查数据时，建议默认：

```text
75分疲劳对应的计划负荷上限 C75 = 18
```

预测疲劳分数：

```text
predictedScore = clamp(round(75 × plannedLoad / C75), 0, 100)
```

当 `plannedLoad = C75` 时，系统预测约为 75 分，表示“已经比较疲劳，应考虑休息或调整任务”。

### 6.3 页面状态与提醒档位

| 预测分数 | 状态 | 行为 |
| --- | --- | --- |
| 0～49 | 舒适 | 正常展示，不提醒 |
| 50～69 | 较满 | 页面内展示负荷状态，不推送 |
| 70～84 | 较疲劳 | 创建/编辑时内联提醒；每天最多一次站内提醒 |
| 85～99 | 高负荷 | 明显提醒，允许用户继续保存 |
| 100 | 可能过载 | 强提醒，仍不禁止保存 |

预测分数用于解释计划，不代表用户真实身体状态。

### 6.4 提醒文案

创建或编辑时：

> 添加后，今天的个人日程预计负荷将达到 86 分，已接近你的当前承受上限。建议调整低紧急程度日程或预留休息时间。

完成任务后：

> 你今天已完成的个人日程累计负荷较高，可以考虑休息一会儿再继续。

禁止使用：

> 你已经过度疲劳。

除非用户自己在调查中给出高分，否则系统不能把预测当成事实。

### 6.5 提醒去重

新增提醒记录唯一维度：

```text
userId + localDate + sourceType + thresholdBand + algorithmVersion
```

规则：

- 同一天同一来源、同一档位最多通知一次。
- 进入更高档位可以再次提醒。
- 两次疲劳通知至少间隔两小时。
- 用户选择“今天不再提醒”后，只有跨入更高档位才允许再次通知。
- 创建和编辑表单优先使用内联提示，不同时发送额外推送。
- 周期任务或批量导入造成大量变化时只发送汇总提醒。

## 七、日终 0～100 疲劳调查

### 7.1 调查问题

默认在用户本地时间 21:30 提醒：

> 今天这些个人日程给你带来的疲劳程度是多少？

使用 0～100 滑块，并提供锚点：

| 分数 | 含义 |
| --- | --- |
| 0 | 完全不累，精力充足 |
| 25 | 有一点累 |
| 50 | 明显疲劳，但还能继续 |
| 75 | 很累，需要休息 |
| 100 | 精疲力尽，不适合继续安排任务 |

问题必须限定为“个人日程带来的疲劳”。团队任务、工作外事务和身体状态都可能造成额外影响，不能直接用总体疲劳训练个人日程模型。

### 7.2 异常因素

调查增加一个低打扰的可选项：

- 今天存在明显的额外影响。
- 可选原因：睡眠不足、身体不适、情绪压力、临时额外事务、高强度运动或出行、存在未记录任务、其他。

异常原因只用于降低当天训练权重，不进行医学判断。

### 7.3 调查触发规则

- 每个用户、每个本地日期最多创建一次调查提醒。
- 当天至少完成一项个人日程才进入正常校准候选。
- 用户可以跳过，不强制填写。
- 当天答案允许修改，保留最后提交值和修改时间。
- 次日首次打开可以补填前一天调查。
- 超过 48 小时补填只保留记录，不参与自动学习。
- 调查提醒遵守用户安静时段和总通知开关。
- 没有个人日程完成记录时不主动打扰用户。

### 7.4 调查页面反馈

提交后展示可解释结果：

```text
系统预计：68分
你的反馈：75分
当前状态：校准中
本次只会小幅调整你的个人上限
```

不要展示“AI 诊断”“健康风险”等医疗化文案。

## 八、个性化疲劳模型

### 8.1 为什么要分阶段

一天只有一个调查分数，无法同时可靠判断五个等级系数和用户承受能力。若一开始全部自动修改，少量异常数据会导致模型失真。

因此先学习个人上限，再在数据充足后小幅调整五档系数。

### 8.2 第一阶段：默认模型

有效调查少于 7 天：

- 使用默认系数 `1/2/3/5/8`。
- 使用默认 `C75 = 18`。
- 页面标记“基础估算”。
- 记录数据但不频繁调整。

### 8.3 第二阶段：个人上限校准

有效调查达到 7 天后，开始估算个人 `C75`。

当天候选上限：

```text
candidateC75 = 75 × completedLoad / clamp(surveyScore, 10, 95)
```

有效训练日要求：

- 当天存在已完成个人日程。
- `completedLoad > 0`。
- 调查在允许时间内提交。
- 没有“存在大量未记录任务”等强干扰因素。
- 当天没有跨时区造成的日期不确定性。

更新方法：

1. 候选值限制在当前上限的 `0.5～1.5` 倍。
2. 使用最近 28 个有效日的加权中位数，近期数据权重略高。
3. 使用平滑更新：`newC75 = 0.85 × oldC75 + 0.15 × candidateMedian`。
4. 单次更新最多变化 ±10%。
5. 最终上限设置合理边界，建议 `5～60` 负荷点。

状态展示：

- 7～20 个有效日：校准中。
- 至少 21 个有效日且跨越 3 周：已个性化。

### 8.4 第三阶段：五档系数微调

只有满足以下条件才调整等级系数：

- 至少 30 个有效调查日。
- 数据跨度至少 4 周。
- 每一个需要调整的疲劳档位至少出现 5 次。
- 用户没有锁定个性化设置。

约束：

```text
weight1 < weight2 < weight3 < weight4 < weight5
```

- 所有权重必须为正数。
- 每个权重相对初始值最多偏移 ±30%。
- 每周最多更新一次。
- 更新后重新计算预测，不修改历史完成快照。
- 数据不足时继续使用初始系数，不制造“伪个性化”。

实现上建议使用带正则约束的回归或网格搜索，不使用自由度过高的模型。

### 8.5 异常调查权重

- 无异常因素：权重 1.0。
- 轻微异常因素：权重 0.5。
- 明显未记录任务、身体不适、跨时区或延迟超过 48 小时：不进入自动学习。
- 某种异常因素在 14 天内重复出现 4 天以上时，不再简单视为一次性异常，应提示用户是否把它纳入长期承受基线。

### 8.6 用户控制权

用户可以：

- 开启或关闭疲劳统计。
- 开启或关闭日终调查。
- 修改调查提醒时间。
- 开启或关闭疲劳提醒。
- 查看当前五档系数和个人上限。
- 锁定个人上限，只接受系统建议而不自动更新。
- 重置为默认模型。
- 删除调查历史并重新校准。

## 十、后端服务与接口设计

### 10.1 服务拆分

建议新增：

- `FatigueService`：负荷计算、日汇总重算、提醒判断、调查提交和模型校准。
- `FatigueController`：用户疲劳概览、偏好、调查和历史接口。
- `FatigueSurveyScanTask`：按照用户本地时间创建日终调查通知。

`ScheduleService` 只负责在日程变化后调用统一的重算入口，不在多个方法中重复编写负荷公式。

### 10.2 日程接口扩展

创建和编辑请求增加：

```json
{
  "urgencyLevel": 4,
  "fatigueLevel": 3
}
```

校验规则：

- 必须是整数。
- 只能在 1～5 之间。
- 字符串、浮点数、空值和越界值返回 HTTP 400。
- 后端不依赖前端默认值，缺失时使用 3。

列表和详情响应增加：

```json
{
  "urgencyLevel": 4,
  "urgencyLabel": "紧急",
  "fatigueLevel": 3,
  "fatigueLabel": "一般",
  "fatigueWeight": 3,
  "completedAt": null
}
```

列表排序增加：

- `urgency_desc`
- `fatigue_desc`
- `time_asc`
- 原有 `manual` 继续保留。

### 10.3 疲劳接口

建议接口：

```text
GET  /api/v1/fatigue/profile
PUT  /api/v1/fatigue/preferences
POST /api/v1/fatigue/profile/reset
GET  /api/v1/fatigue/daily?date=2026-08-10
GET  /api/v1/fatigue/history?dateFrom=2026-08-01&dateTo=2026-08-10
GET  /api/v1/fatigue/survey/today
POST /api/v1/fatigue/surveys
PUT  /api/v1/fatigue/surveys/{localDate}
POST /api/v1/fatigue/preview
```

`POST /api/v1/fatigue/preview` 只做未保存变更的试算，不写入日程或调查数据。Web 和桌面创建/编辑器都调用同一接口，返回变更前后负荷、预计分数、提醒档位和主要贡献项，避免两端各自复制疲劳公式。接口需要带上用户时区和操作日期，并明确是新建、编辑还是删除预览。

提交调查：

```json
{
  "localDate": "2026-08-10",
  "score": 75,
  "externalFactorLevel": 0,
  "externalFactorTags": []
}
```

当天概览响应：

```json
{
  "localDate": "2026-08-10",
  "plannedLoad": 16,
  "completedLoad": 8,
  "predictedScore": 67,
  "capacity75": 18,
  "level": "full",
  "modelStage": "calibrating",
  "confidence": "medium",
  "topContributors": [
    {
      "scheduleId": 123,
      "title": "准备项目汇报",
      "fatigueLevel": 5,
      "weight": 8
    }
  ]
}
```

### 10.4 日程操作后的重算入口

以下路径必须调用同一个 `FatigueService.recalculateDates(...)`：

- 用户创建、编辑、删除日程。
- 完成、恢复完成、取消、恢复取消。
- 移动日期或修改时间类型。
- 管理员修改日程状态。
- 用户修改时区。

建议事务内只记录需要重算的用户与日期，在事务提交后执行汇总计算和通知，避免因为发送通知导致日程事务失败。

### 10.5 通知类型

新增：

- `fatigue_plan_warning`
- `fatigue_actual_warning`
- `fatigue_survey`

通知响应建议同时携带 `type`、`localDate`、`targetRoute`、`targetId` 和 `dataRevision`，供 Web、完整桌面窗口和快捷小窗口统一导航与去重。`NotificationService` 必须显式识别这些类型，不能让它们错误地跟随团队任务状态通知开关。

## 十一、用户端交互设计

### 11.1 创建和编辑表单

增加两个五档分段控件：

```text
紧急程度：1  2  3  4  5
预计疲劳：1  2  3  4  5
```

要求：

- 选中项同时显示数字和中文解释。
- 不能只靠颜色区分。
- 紧急程度和疲劳程度使用不同图标与标签，避免用户混淆。
- 移动端保持稳定尺寸，必要时使用两行布局，不能横向溢出。
- 默认值 3 明确选中。
- 提交前展示添加后的当天预计负荷。

### 11.2 AI 草稿确认

- AI 日程解析仍然只产生草稿，不直接写库。
- 新建表单首次打开时紧急程度和疲劳程度默认都是 3。
- 用户在点击 AI 解析前已经选择的两个等级，必须原样带入 AI 草稿，不能被解析结果重置。
- 即使 AI 将来提供建议，也必须标记为“建议值”，由用户在确认弹窗中选择。
- `confirmAiDraft` 必须把两个字段一起写回普通日程表单。

AI 草稿链路需要同时覆盖：

1. `aiDraft` 类型与初始值。
2. `aiParseSchedule()` 创建草稿时保留用户等级。
3. `confirmAiDraft()` 写回普通表单。
4. AI 草稿确认窗口中的五档控件。

### 11.3 日程卡片

建议展示：

```text
紧急 4 · 预计疲劳 3
```

- 紧急程度使用文字、数字和警示图标。
- 疲劳程度使用文字、数字和能量图标。
- 逾期状态继续优先于普通等级颜色。
- 已完成卡片可以显示完成时系数快照，避免历史显示随模型变化。

### 11.4 今日负荷区域

个人日程页和首页个人区域显示：

```text
今日预计负荷 16 / 个人上限 18
今日已完成负荷 8
模型状态：校准中
```

团队任务区域不显示在这组统计中。

### 11.5 日终调查界面

- 使用 0～100 滑块或步长为 5 的数值选择。
- 展示 0、25、50、75、100 五个文字锚点。
- 可以选择异常因素，但不是必填。
- 支持“稍后提醒”和“跳过今天”。
- 提交后展示系统预测与用户反馈的差异。
- 不展示医疗结论。

### 11.6 前端代码组织建议

- `types/index.ts`：新增 `ScheduleLevel = 1 | 2 | 3 | 4 | 5`、`ScheduleViewMode`，并扩展 `Schedule`、`ScheduleForm`。
- `utils/helpers.ts`：`toSchedulePayload()` 必须发送 `urgencyLevel` 和 `fatigueLevel`。
- 新建 `utils/scheduleView.ts`：集中实现时间分桶、五档文案、稳定排序和分区键，避免继续膨胀 `SchedulesPage.vue`。
- `stores/app.ts`：增加 `scheduleViewMode`；创建成功后的表单重置必须把两个等级恢复为 3。
- `SchedulesPage.vue`：增加分段切换、负荷摘要、卡片等级、AI 草稿字段以及模式相关操作限制。
- `ScheduleDetailPage.vue`：详情展示、编辑回填和提交两个等级。
- `components/ScheduleForm.vue`：若继续保留，必须同步字段；若确认无引用，应在独立清理任务中删除。
- 可提取 `ScheduleLevelPicker.vue`、`ScheduleViewSwitcher.vue` 和 `ScheduleSection.vue`，减少创建、详情和草稿确认之间的重复。
- 模式切换产生的新请求必须带版本或取消旧请求，避免较慢的旧响应覆盖用户刚选择的新模式。

## 十二、隐私、安全与可解释性

- 疲劳调查、异常原因和个性化上限属于用户私密数据。
- 团队管理员、团队成员和普通后台管理员默认不能查看明细。
- 管理后台如需运营统计，只提供匿名聚合，并另外设计权限与审计。
- 计算过程不把任务标题、调查内容或异常原因发送给外部 AI。
- 日终调查原始数据建议默认保留 180 天，超过期限按产品隐私策略删除或匿名化。
- 用户删除调查历史后，需要重新计算或重置个性化模型。
- 每次提醒应提供负荷来源、主要贡献任务、当前模型阶段和采用的算法版本。
- 页面明确注明：“该功能用于日程负荷估算，不属于医疗诊断或健康建议。”

### 阶段 3：日终调查与上限校准

- 有效数据达到要求后，小幅调整五档系数。

- 评估是否加入预计投入时间、实际投入时间、时间冲突和跨天精确分摊。

## 十四、测试计划

### 14.1 后端测试

- 创建和编辑接受 1～5 的整数值。
- 缺失值使用默认 3。
- 0、6、浮点数、字符串和空值被拒绝。
- 用户不能读取或修改其他用户的疲劳数据。
- 团队任务不会进入个人日程分区和疲劳计算。
- 完成任务后计划总负荷不下降，实际任务负荷增加。
- 取消和删除后计划负荷正确减少。
- 恢复完成后实际负荷和完成快照正确回滚。
- 修改日期时原日期和新日期都正确重算。
- 用户时区边界、午夜前后和夏令时日期归属正确。
- 同一天同档位提醒并发请求只产生一条。
- 跨入更高档位可以产生新提醒。
- 调查每个用户每天唯一。
- 超过 48 小时的调查不参与学习。
- 异常因素日降低权重或排除。
- 个性化上限单次变化不超过 10%。
- 五档系数始终正数且严格递增。
- 历史完成快照不会被新系数覆盖。
- 管理员状态修改也触发统一重算。

### 14.2 用户端测试

- 新建、编辑和 AI 草稿确认都提交两个等级字段。
- 五档控件键盘、鼠标和触摸操作正常。
- 时间、分组、紧急和疲劳模式切换正确。
- 四种模式只展示个人日程。
- 筛选条件在切换模式后保持。
- 当前用户的查看模式可以恢复。
- 非分组模式不允许手动拖拽排序。
- 卡片文字和图标与等级一致。
- 移动端不发生文字或控件重叠。
- 调查滑块只能提交 0～100。
- 页面能区分预计分数和用户实际反馈。
- 提醒失败不会阻止日程保存。

### 14.3 验收场景

场景一：

1. 用户创建三项个人日程，疲劳等级分别为 2、3、5。
2. 系统使用默认系数计算负荷 `2 + 3 + 8 = 13`。
3. 团队任务即使同一天存在，也不进入该结果。
4. 用户切换到“按疲劳”后，等级 5 的个人日程显示在最前。

场景二：

1. 用户完成等级 5 的个人日程。
2. 计划负荷保持不变。
3. 实际任务负荷增加 8。
4. 完成时保存系数快照。

场景三：

1. 用户日终反馈 80 分。
2. 系统保存当日完成负荷、系数、时区和异常因素快照。
3. 有效调查不足 7 天时不立即大幅调整上限。
4. 满足校准条件后，上限只进行受限的小幅更新。

场景四：

1. 同一天连续添加多项高疲劳个人日程。
2. 第一次跨入 70 分档位产生提醒。
3. 在同一档位继续增减任务不重复发送。
4. 跨入 85 分档位后允许发送一次更高级别提醒。

---

## 十五、上线与回滚策略

- 使用功能开关控制疲劳统计、提醒和调查，四种视图可以先独立上线。
- 数据迁移只新增字段和表，不删除旧字段。
- 第一阶段上线时禁止根据历史完成任务批量触发通知。
- 先向测试账号开放，再逐步扩大范围。
- 监控调查填写率、跳过率、提醒关闭率和模型异常变化。
- 如果个性化算法出现问题，可以关闭自动学习，继续使用默认系数和默认上限。
- 回滚应用版本时，新字段保留但旧代码忽略，不立即删除数据。

## 十六、实施前需要最终确认的产品口径

以下内容在本方案中采用推荐值，正式编码前应由产品确认：

1. 紧急程度是否最终确定为数字越大越紧急，5 最高。
2. 疲劳等级初始系数是否确定为 `1/2/3/5/8`。
3. 新建日程两个等级是否都默认选择 3。
4. 默认个人 `C75` 是否采用 18。
5. 日终调查默认时间是否采用用户本地时间 21:30。
6. 跨多天持续任务第一版是否只归入开始日期。
7. 已完成任务恢复为待完成后，是否允许再取消。
8. 疲劳原始调查默认保留期限是否采用 180 天。
9. 第一期是否严格不加入预计耗时乘数，只使用用户选择的五档系数。

当前推荐结论：先完成简单、透明、可解释的五档模型和四种个人视图，再用日终调查逐步学习个人上限；数据达到要求后才允许调整五档系数。
