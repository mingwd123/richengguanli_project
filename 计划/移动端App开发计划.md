## 2. 产品目标

移动端不是重新做一个新产品，而是把现有日程与团队任务能力变成适合单手操作、及时提醒和碎片化查看的 iOS / Android App。

### 2.1 核心目标

- 在手机上完成登录、查看、创建、编辑和完成日程。
- 在手机上处理团队任务：接受、拒绝、完成、取消、恢复和重新分配等已有权限范围内的操作。
- 通过系统推送及时接收任务分配、状态变化和截止提醒。
- 保持 Web 端已经确认的时间、状态、权限、通知和 AI 草稿规则一致。
- 延续现有“轻盈科技感”界面：浅色工作区、细网格背景、青绿色主色、蓝色/珊瑚色/琥珀色状态辅助色，以及轻量动画。
- 让移动端成为用户端，不承担管理员数据管理和后台审计职责。

### 2.2 非目标

第一版移动端不包含以下内容：

- 管理员移动后台。
- 聊天、文件附件、支付和企业审批。
- 微信登录、短信验证码登录、邮箱登录、忘记密码。
- 甘特图、复杂权限系统、团队转让。
- 复杂 AI 自动排程。
- 一开始就承诺完整离线编辑和多人离线冲突合并。
- 直接连接 MySQL。App 只能通过后端 API 访问数据。

## 3. 版本拆分

移动端版本号与产品 Web 端的 MVP / V1.1 / V1.2 对齐，但不重复创建三套后端功能。

### M0：移动端基础工程

目标：可以在 Android 模拟器或真机启动一个能登录的 Capacitor App。

- 创建 `src/mobile` 工程。
- 接入 Vue 3、TypeScript、Vite、Pinia、Vue Router 和 Capacitor。
- 建立移动端环境配置和 API 地址切换能力。
- 建立安全 Token 存储抽象，不让页面直接操作 `localStorage`。
- 建立 iOS / Android 平台目录和原生权限清单。
- 复用现有用户端类型、API、Pinia store 和工具函数，避免复制业务逻辑。
- 完成 App 启动、登录、退出、刷新 Token 和恢复会话。

### M1：移动端 MVP 对齐版

目标：覆盖现有 MVP 的用户端核心流程。

- 手机号 + 密码登录注册。
- 首页总览：今日待办、未来七天、个人日程、团队任务和时间轴。
- 个人日程：创建、编辑、软删除、取消、完成、恢复、筛选和分页。
- 日历：按月份查看、点击日期查看当天个人日程和团队任务、当天时间轴。
- 团队：创建团队、邀请码加入、查看成员、查看角色和退出/移除等权限内操作。
- 团队任务：创建、选择执行人、接受、拒绝、完成、取消、恢复和查看执行状态。
- 团队任务详情：操作时间轴、执行人状态、重新分配入口和权限提示。
- 站内通知：分页、已读、全部已读、通知详情和跳转业务详情。
- 提醒记录：查看待发送、已发送、已取消和失败记录。
- 我的：个人资料、头像、时区、主题、通知偏好、AI 数据记录开关和修改密码。
- 移动端退出登录和账号失效后的统一回到登录页。

### M1.1：原生通知与 V1.1 / V1.2 体验对齐

目标：让移动端不仅能“查看”，还能按照已有 Web 端增强规则高效操作。

- 接入 APNs / FCM 推送。
- 设备注册、注销、Token 轮换和多设备管理。
- 推送点击后通过深链接打开通知对应的日程、团队任务或通知详情。
- 推送分类：任务分配、任务状态变化、到期提醒、团队动态。
- 复用 V1.1 的 AI 功能：自然语言创建日程、团队任务拆解、今日计划建议、描述优化。
- AI 结果必须先进入可编辑草稿，用户确认后才能调用正常保存接口，禁止 AI 直接写库。
- 复用 V1.1 / V1.2 的分组、排序、折叠、逾期置顶、倒计时和时间轴规则。
- 将 Web 端右键菜单替换成移动端长按菜单或“更多”底部操作面板。
- 将桌面拖拽排序替换为长按拖动、上移/下移按钮或移动到分组操作，避免依赖精确拖拽。
- 支持日间/夜间主题、系统主题跟随和低动态模式。

### M1.2：发布质量与体验优化

目标：达到可邀请真实测试用户使用的稳定程度。

- 增加网络中断、请求超时、Token 失效、推送权限关闭等明确状态。
- 对首页和最近访问页面增加轻量缓存，恢复 App 时优先展示上次数据，再后台刷新。
- 支持草稿保存，避免用户填写日程或任务时被系统回收导致内容丢失。
- 增加推送权限引导、系统设置跳转和通知诊断页。
- 增加 Android 返回键、iOS 页面返回、键盘收起和安全区域适配。
- 完成真机测试、崩溃日志、构建签名和灰度发布流程。

## 4. 技术架构

### 4.1 推荐技术栈

| 层级 | 选择 | 说明 |
| --- | --- | --- |
| App 壳 | Capacitor | 将 Vue 用户端打包为 iOS / Android App |
| 前端 | Vue 3 + TypeScript + Vite | 与现有用户端保持一致 |
| 状态 | Pinia | 复用登录、首页、通知、日程、团队和任务状态 |
| 路由 | Vue Router | 复用业务路由，并增加深链接映射 |
| 网络 | 现有 API 封装 | 统一处理 Access Token、Refresh Token、错误和超时 |
| 本地安全存储 | 原生 Keychain / Android Keystore 封装 | Token 不直接放普通网页存储 |
| 推送 | APNs + FCM | 通过 Capacitor 插件接入，后端统一发送 |
| 数据库 | 后端 MySQL | App 不直接连接数据库 |

### 4.2 代码复用原则

复用应优先从模块边界开始，而不是复制整个 `web-user` 目录。

1. 先复用 `types`、`api`、`stores`、`utils` 和纯逻辑组件。
2. 页面结构根据移动端屏幕重新编排，不强行复用桌面布局。
3. 逐步把稳定的公共模块提取到 `src/shared`，再由 Web、桌面端和移动端引用。
4. `admin-web` 保持独立，不把管理员 store、页面和权限菜单带入用户 App。
5. 移动端专属能力放在 `src/mobile/src/platform`，例如推送、深链接、安全存储、原生返回键。
6. API 请求仍统一从 API 层发起，页面不得直接拼接请求地址或访问数据库。

## 5. 移动端页面与导航

### 5.1 底部主导航

移动端采用五项底部导航，保证单手操作和快速切换：

1. 首页：今日概览、AI 今日计划、未来七天和时间轴。
2. 日程：月历、当天时间轴、个人日程列表和新建日程。
3. 任务：我的团队任务、团队筛选、任务状态和新建团队任务。
4. 通知：站内通知、提醒记录和通知偏好入口。
5. 我的：个人资料、主题、时区、AI 隐私设置、账号和关于。

团队列表从“任务”页或“我的”页进入；不把八个 Web 导航入口全部塞进底部导航。

### 5.2 移动交互替换规则

| Web 交互 | 移动端交互 |
| --- | --- |
| 右键菜单 | 长按菜单或“更多”按钮打开底部操作面板 |
| 拖拽排序 | 长按拖动；无法稳定拖动时提供上移、下移和移动到分组 |
| 桌面弹窗 | 底部 Sheet 或全屏编辑页 |
| 列表分页 | 上拉加载、下拉刷新和明确的加载状态 |
| 删除操作 | 二次确认；不使用滑动即删除 |
| 任务完成 | 点击完成按钮后短暂反馈，并保留撤销入口 |
| 时间字段 | 使用适合触屏的日期时间选择器，明确显示用户时区 |
| 桌面悬停详情 | 点击状态/倒计时标签打开详情面板 |

### 5.3 视觉和可用性要求

- 延续现有“轻盈科技感”视觉；新增移动端产品文案统一使用 `dayline`，不在本计划中大范围重命名历史目录或既有代码标识。
- 主色继续使用青绿色，蓝色表示普通任务或持续任务，琥珀色表示临近到期，珊瑚/红色表示逾期，绿色表示完成。
- 所有可点击控件的触控区域不小于 44px。
- 适配刘海屏、底部 Home Indicator 和 Android 导航栏安全区域。
- 处理小屏文字换行、键盘遮挡、横屏异常和长标题截断。
- 不依赖 hover，不把关键操作藏在只有鼠标才能触发的交互里。
- 动画轻量，支持 `prefers-reduced-motion` 和系统减少动态效果设置。
- 暗色模式必须保证状态色、输入框和弹窗对比度足够。

## 6. 业务规则对齐

移动端必须沿用现有文档和后端接口的规则，不在 App 内自行推导出另一套状态。

### 6.1 时间与时区

- 数据库继续统一保存 UTC 时间。
- 接口继续使用带时区的 ISO8601 时间。
- App 根据用户设置的时区显示日期、时间、倒计时和逾期状态。
- 日历日期匹配必须使用用户时区，避免 UTC 日期和本地日期错位。
- AI 解析自然语言时明确使用用户时区。

### 6.2 日程和任务

- 保持 `point_event`、`deadline_task`、`duration_task` 的时间轴展示语义。
- 逾期只影响展示和提醒，不自动修改业务状态。
- 已完成和已取消任务不继续显示倒计时。
- 个人日程和团队任务继续支持分组折叠、逾期置顶、完成分组和排序。
- 团队任务继续遵守 owner > admin > member 权限关系。
- 多人协作任务、拒绝后重新分配、取消后恢复和执行人历史记录按现有 V1.2 规则处理。
- 移动端只显示当前用户有权限的操作，不能通过隐藏按钮绕过后端权限校验。

### 6.3 通知

- 站内通知仍是服务端事实来源，系统推送只是到达提醒渠道。
- 用户关闭系统推送后，站内通知仍然保留。
- 用户通知偏好继续区分任务分配、任务状态、到期提醒和浏览器/设备通知。
- 完成、取消、拒绝或重新分配后，相关提醒必须按现有联动规则取消或重新生成。
- 用户点击推送后必须打开对应业务详情，并在登录失效时先完成登录再回跳。

### 6.4 AI

- 移动端复用现有 AI 接口，不在 App 端保存 API Key。
- AI 日程解析、团队任务拆解和描述优化只返回草稿/建议。
- 用户可以在移动端编辑草稿，点击确认后才调用普通创建或更新接口。
- 用户关闭 AI 数据记录后，不应在客户端或后端保存不必要的 input/output。
- AI 不可用时，普通手动创建流程必须仍然可用。

## 7. 后端与原生能力补充

移动端可以先复用现有业务接口，但原生推送需要增加最小的设备能力接口。

### 7.1 建议新增设备接口

```text
POST   /api/v1/devices/register
DELETE /api/v1/devices/{deviceId}
PUT    /api/v1/devices/{deviceId}/token
GET    /api/v1/devices
```

建议字段：

- `device_id`
- `user_id`
- `platform`：`ios` / `android`
- `push_token`
- `app_version`
- `os_version`
- `timezone`
- `locale`
- `last_seen_at`
- `status`

设备接口要求：

- 同一设备 Token 更新时复用记录，不重复创建无限设备记录。
- 用户退出登录时注销当前设备或撤销当前用户绑定。
- 推送失败、Token 失效时记录原因并停止继续投递到失效 Token。
- 用户可以在 App 内查看并撤销其他登录设备。
- 后端不能把推送 Token 当作密码或 JWT 保存到普通日志中。

### 7.2 推送发送服务

- 后端新增统一 Push Provider 抽象，分别接入 APNs 和 FCM。
- 业务通知先生成站内通知，再根据用户偏好和设备状态决定是否发送推送。
- 推送内容只包含必要摘要，不在锁屏通知中泄露过多任务描述或敏感信息。
- 推送 payload 携带业务类型和资源 ID，例如 `schedule_id`、`team_task_id`、`notification_id`。
- 推送点击深链接由 App 路由层解析，不能让服务端拼接不受控 URL。
- 推送发送需要有重试、失败记录和去重策略，避免提醒重复弹出。

### 7.3 深链接

建议统一使用 `dayline://` 技术 scheme，并预留 HTTPS Universal Links / App Links：

```text
dayline://home
dayline://calendar/2026-08-02
dayline://schedules/123
dayline://tasks/456
dayline://notifications/789
```

深链接处理顺序：

1. App 未启动：记录待处理链接，完成启动和鉴权后消费。
2. App 已登录：直接打开目标页面并刷新详情。
3. App 未登录：先跳转登录，登录成功后回到目标页面。
4. 目标资源不存在或无权限：显示稳定错误信息，不泄露后端内部异常。

### 7.4 数据库命名约束

- 后端、Docker、测试和部署环境的数据库名称统一使用 `dayline`。
- 移动端永远不直接配置或连接数据库名称；它只配置 API 地址。
- `dayliane` 不得再作为数据库名称使用。
- 当前产品文案、Java 包名和历史目录不在本计划中大范围重命名。

## 8. 认证、安全与隐私

### 8.1 Token 和会话

- Access Token 和 Refresh Token 继续遵守现有 JWT 设计。
- Access Token 只放内存或短期可用存储；Refresh Token 放原生安全存储。
- 统一封装 `TokenStorage`，页面和业务组件不能直接调用原生存储 API。
- App 从后台恢复时检查 Token 是否过期，必要时刷新；刷新失败则清理会话并回登录页。
- 多次请求同时发现 Token 过期时，只允许一个刷新流程运行，避免刷新风暴。

### 8.2 权限和输入

- 所有团队、日程和任务操作继续由后端进行对象级权限校验。
- App 端的按钮显示只是体验层，不能作为安全边界。
- 自然语言、标题、描述、分组名和邀请码都要做长度限制、错误提示和提交前校验。
- 不在客户端打包 AI API Key、数据库密码、JWT Secret 或内部扫描 Token。

### 8.3 当前安全延期的影响

`计划/后续计划.md` 中的固定明文演示账号和异常 HTTP 状态问题目前仅允许本机或受控测试网络使用。移动端进入公测、上架或连接真实用户数据前，必须先完成这两项整改并重新验收。

## 10. 验收标准

### 10.1 功能验收

- 用户可以完成注册、登录、刷新会话、退出和修改密码。
- 用户可以在手机上完成个人日程全流程，并在日历和首页看到一致数据。
- 用户可以完成团队创建/加入、成员查看和权限内成员操作。
- 用户可以完成团队任务的创建、接受、拒绝、完成、取消、恢复和重新分配流程。
- 团队任务详情可以展示操作时间轴，且操作后立即刷新。
- 通知和提醒记录可查询、已读、全部已读，并能跳转到业务详情。
- AI 只生成可编辑草稿，用户确认前不会写入日程或任务数据。

### 10.2 原生能力验收

- App 在前台、后台和完全退出后都能正确处理推送点击。
- 推送权限关闭时，App 明确提示并保留站内通知。
- 多设备登录时 Token 和推送设备记录不互相覆盖。
- 退出登录后当前设备不再收到该账号的推送。
- Android 返回键和 iOS 返回手势不会破坏表单或导航状态。
- 刘海屏、底部 Home Indicator 和键盘不会遮挡主要操作。

### 10.3 工程验收

- 移动端不直接复制一份长期分叉的业务 store/API。
- 不在移动端提交密钥、数据库密码、推送私钥或测试环境之外的固定账号。
- `dayline` 是所有后端数据库配置中的唯一正确数据库名。
- 用户端、桌面端、移动端的时间和权限规则一致。
- 关键页面无横向溢出、无控制台错误、无未处理 Promise 错误。
- 后端测试、用户端测试、管理员端测试和移动端测试全部通过后才进入发布候选。

## 11. 测试用例重点

### 11.1 认证

- 正确手机号和密码登录。
- 错误密码、空字段、弱密码和登录失败限流提示。
- Access Token 过期后自动刷新。
- Refresh Token 失效后清理会话并回到登录页。
- App 被杀死后重新打开仍能正确恢复或要求重新登录。

### 11.2 时间和任务

- 上海时区和其他时区下日期显示一致。
- 瞬时日程、截止任务、持续任务在手机时间轴中表达正确。
- 逾期任务置顶但不改变业务状态。
- 多执行人任务的接受、拒绝、完成和整体状态符合现有规则。
- 被移除成员不能继续操作旧团队，但管理员仍能看到历史记录。

### 11.3 通知

- 分配任务、接受/拒绝/完成、重新分配、取消和到期提醒均能按偏好发送。
- 推送重复到达时 App 不重复创建站内通知。
- 点击推送能打开对应详情；无权限或资源不存在时显示稳定提示。
- 系统通知关闭后，站内通知仍能正常使用。

### 11.4 AI

- 自然语言解析失败时保留原输入。
- 草稿可编辑，取消确认不会写库。
- 关闭 AI 数据记录后不记录不必要的 input/output。
- AI 服务不可用时手动创建仍然可用。

## 12. 风险与处理

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| Web 页面和移动页面强行共用布局 | 小屏操作拥挤、后续难维护 | 共享业务模块，移动端单独布局 |
| 推送 Token 失效或重复注册 | 用户收不到或重复收到通知 | 设备表、Token 更新、失败清理和发送日志 |
| iOS 构建依赖 macOS / Xcode | Windows 本机无法完成 iOS 正式包 | 先完成 Android 和 Web 验证，使用 macOS CI 或开发机发布 iOS |
| App 被系统回收 | 表单内容或导航状态丢失 | 表单草稿、启动恢复、后台刷新 |
| 离线编辑产生冲突 | 数据被覆盖或状态错误 | 第一版只做缓存和重试，完整离线编辑延后 |
| 移动端绕过前端隐藏按钮调用接口 | 越权修改数据 | 所有权限以后端鉴权和对象级校验为准 |
| 生产仍存在固定明文账号 | 账号被接管 | 依照 `后续计划.md` 的上线门禁，整改前只允许本机或受控网络 |
| 数据库名称继续写错 | 连接到空库或错误库 | 统一检查 `DB_NAME=dayline`，App 只配置 API 地址 |

## 13. 开发完成定义

移动端开发只有同时满足以下条件，才算完成第一阶段：

1. M1 的核心用户流程在 Android 和 iOS 至少各有一套可运行验证环境。
2. 现有 Web 端与移动端使用同一套后端业务规则，关键状态和时间结果一致。
3. 推送注册、注销、点击深链和通知偏好通过真实设备验证。
4. Token 使用原生安全存储，生产构建不包含测试密钥和数据库凭据。
5. 移动端页面完成小屏、安全区域、键盘、返回键和断网状态验收。
6. `src/mobile` 的测试、构建和文档齐全，且不会破坏 `src/web-user`、`src/desktop`、`src/admin-web` 和 `src/backend`。
7. 生产部署前完成 `后续计划.md` 中暂缓的安全整改，并确认数据库使用 `dayline`。
