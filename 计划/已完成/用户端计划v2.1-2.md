## 一、版本目标

v2.1 的核心不是引入新的工时系统，而是**把现有「用户自选 1～5 级疲劳 + 个人化算法适配」做成稳定闭环**，同时让团队任务的真实完成感受能够被看见，但不污染个人模型。

重点方向：

1. 保留个人日程的 1～5 级疲劳选择，由算法独立适配每位用户的疲劳权重与精力上限。
2. 团队任务完成时由当前执行人选择完成疲劳程度，按执行人分别记录，并只计入完成日的展示负荷。
3. 为个人跨天 / 长期日程增加可选的每日进度记录，让用户按当天实际推进比例和疲劳程度归集完成负荷。
4. 补齐「周期 / 重复任务」这一效率工具的基础能力，降低用户流失。
5. 新增「周 / 月疲劳与负荷回顾报告」，把日终调查沉淀成持续可回看的价值。
6. 把 AI 从"解析 / 拆解 / 建议"的被动翻译，升级为基于疲劳系数的「主动排程建议」。
7. 提供日历 iCal 订阅 / 导出，降低用户迁移与导入成本。

本版本明确不做：基于分钟的疲劳模型、预计/实际投入时长字段、系统自动跨天分摊、团队任务多人均摊，以及团队任务的重复规则。个人跨天 / 长期日程仅允许按用户主动提交的每日进度归集负荷，团队任务仍只按执行人完成日结算。

## 二、数据库与后端变更

### 2.1 个人日程疲劳模型与完成快照

| 变更 | 说明 |
|------|------|
| `schedule.fatigue_level` | 用户为个人日程选择的计划疲劳程度（1～5） |
| `schedule.completed_fatigue_level` | 完成负荷快照等级（默认沿用计划等级，1～5） |
| `schedule.completed_fatigue_weight` | 按该用户当时的个性化权重计算并冻结的完成负荷快照 |
| `schedule.progress_tracking_enabled` | 是否启用个人长期任务每日进度模式，默认 `false` |
| `schedule.progress_percent` | 当前累计进度，范围 0～100，默认 0 |
| `schedule_progress_daily` | 个人长期任务每日进度与疲劳快照，按任务、用户和用户时区日期唯一 |
| `user_fatigue_profile` | 每位用户独立维护疲劳权重、精力上限、学习状态与开关 |

规则约定：

- 用户继续直接选择 1～5 级疲劳程度；算法将等级映射为该用户自己的权重，不使用统一的分钟换算。
- 计划负荷使用当前用户权重计算，完成负荷使用完成时保存的疲劳快照计算；同一等级对不同用户可以得到不同负荷。
- 个人日程完成、重新打开、取消或修正状态时，按受影响的计划日与完成日重算摘要；历史数据沿用现有字段，不做分钟口径迁移。
- 本版本不新增 `estimated_minutes`、`actual_minutes`、`span_allocated` 或 `schedule_allocation`，日终调查不新增“今日实际投入”字段。
- 仅个人日程可以开启每日进度模式；适用于跨天日程或用户主动标记的长期任务，普通单日任务默认继续使用原有一次性完成流程。
- 每日进度使用累计百分比 0～100 展示；用户提交新的累计进度时，后端计算本次正向增量。正常操作只允许进度增加，历史回退必须进入修正流程并重算受影响日期。
- 当日进度增量大于 0 且疲劳追踪开启时，必须选择该部分对应的 1～5 级疲劳程度，并冻结该用户当时的个性化权重。追踪关闭时允许只记录进度，不产生疲劳负荷快照。
- 每日进度负荷按 `progressDelta / 100 × fatigueWeightSnapshot` 计算并冻结，归入用户时区下的提交日期；同一任务同一天重复调整采用幂等更新，不得重复累计负荷。
- 进度达到 100% 时自动完成任务，完成日取达到 100% 的用户时区日期；不得再额外写入整项任务的普通完成负荷，避免与每日进度负荷重复计算。
- 进度不足 100% 时点击完成，必须先将剩余比例作为当日进度提交并选择该部分疲劳等级；不得绕过进度记录直接生成整项完成快照。
- 每日进度负荷属于个人日程完成负荷，进入个人日汇总、日终调查、疲劳模型与回顾报告；计划负荷仍沿用任务原有计划疲劳等级，本版本不自动把计划负荷摊到日期区间。
- 暂停、延期或取消任务时保留已经发生的每日进度和疲劳历史；重新打开、删除进度或修正历史进度时，必须重算相关日期摘要和训练样本。
- `schedule_progress_daily` 至少保存 `schedule_id`、`user_id`、`progress_date`、`progress_delta`、`cumulative_progress`、`fatigue_level`、`fatigue_weight_snapshot`、`completed_load` 与审计时间，并对 `(schedule_id, user_id, progress_date)` 建立唯一约束。
- 团队任务不使用每日进度模型，不在认领或执行过程中记录进度疲劳，继续只在当前执行人最终完成时选择疲劳等级并计入完成日。

### 2.2 团队任务完成疲劳记录

- `team_task_assignee` 新增 `completed_fatigue_level`（1～5）与 `completed_fatigue_weight`；复用现有 `completed_at` 作为完成时间。
- 现有 `POST /api/v1/team-tasks/{id}/complete` 在疲劳追踪开启时要求必填请求体 `fatigueLevel`，由当前执行人提交自己的完成疲劳程度，并在同一事务内按该用户当时的权重保存快照；追踪关闭时可省略。
- 当当前用户关闭 `fatigueTrackingEnabled` 或疲劳功能处于灰度关闭状态时，仍允许完成团队任务；此时 `fatigueLevel` 可省略，不保存疲劳快照，也不增加 `teamCompletedLoad`。
- 多执行人任务按执行人分别完成、分别记录；疲劳等级和权重不得放在 `team_task` 主表上，也不做多人均摊。
- 团队任务只在该执行人的**完成日（按用户时区）**增加 `teamCompletedLoad`，不回填计划日、截止日或其他日期。
- 沿用现有 `GET /api/v1/home/today` 与 `GET /api/v1/fatigue/daily`，不新增 `load-summary` 接口；在 `home/today.fatigue` 和现有 `FatigueDailySummary` 中增加 `teamCompletedLoad`、`totalCompletedLoad`，并保持 `completedLoad` 只代表个人日程完成负荷。
- 完成操作必须在同一事务内锁定当前用户的 `team_task_assignee` 记录，校验 `accepted -> completed`，同时成组写入 `completed_at`、疲劳等级和权重快照；重复点击按幂等请求处理，不得重复写快照或重复计入负荷。
- 团队完成负荷不参与日终调查训练、个性化权重/精力上限校准、疲劳预测分数、疲劳提醒或 AI 排程输入；团队完成不得触发个人训练样本失效或模型重训。为兼容现有模型，接口中的 `completedLoad` 继续表示个人日程完成负荷。
- 管理员/创建者的执行人状态修正目标值仅允许 `pending`、`accepted`、`rejected`，不得代替执行人直接设为 `completed`；把已完成执行人修正为非完成状态时，必须清除 `completed_at`、疲劳等级和权重快照并重算原完成日。团队任务整体已处于 `completed` 时沿用当前规则，不提供重新打开入口。
- 在团队任务整体尚未 `completed` 且当前版本状态机允许的重开 / 状态纠正场景中，删除原完成日贡献；再次完成时只写入新的完成日。任务后续取消、软删除或重分配不删除已完成执行人的历史贡献。
- 团队任务不支持跨天分摊、预计时长或重复规则。
- 默认只向当前用户返回自己的完成疲劳等级与权重，其他执行人的疲劳信息不对外公开。
- 完成疲劳等级与权重不得写入 `team_task_event`、通知内容、团队公共详情或普通管理员操作日志，只能在当前用户自己的任务视图与个人统计中读取。
- 疲劳追踪关闭或灰度关闭时，新的团队完成允许无等级且不保存快照、不增加 `teamCompletedLoad`；已存在的快照不删除，关闭期间仅隐藏团队疲劳展示，重新开启后恢复展示。快照沿用现有疲劳数据保留期限，用户删除账户或疲劳数据时同步删除。
- 团队历史展示以执行人快照为准，不因任务后来取消、重分配或软删除而丢失已完成执行人的贡献；查询不得只过滤 `team_task.status='completed'`。

### 2.3 周期 / 重复任务

| 变更 | 说明 |
|------|------|
| `schedule.rrule` | RFC 5545 规则字符串（`FREQ=DAILY/WEEKLY/MONTHLY` 等），可空表示非重复 |
| `schedule.series_id` | 重复系列标识，同一系列的多次实例共享 |
| `schedule.occurrence_date` | 当前实例归属日期 |
| `schedule_series_exdate` | 系列排除日期：`series_id`、`excluded_date`，唯一约束为 `(series_id, excluded_date)` |

规则约定：

- 仅个人日程支持重复；创建或进入新月份时只物化当前自然月实例，按月滚动续注入，避免一次性写入大量未来数据。
- 实例物化对 `(series_id, occurrence_date)` 做幂等约束，重复续注入不会生成重复实例。
- 当前月物化在创建系列、编辑系列、列表 / 日历查询和进入新月份时触发一次幂等续注入；失败可重试，不重复生成实例。
- 每个实例继承系列的 `fatigue_level`；完成 / 取消单个实例不波及其他实例，支持“修改本实例”与“修改整个系列”。
- 支持排除日期（EXDATE）；排除实例不生成、不占负荷、不出现在日历中，已完成实例保留。
- 系列编辑只影响未来未完成实例；系列删除时清理未发生实例，已完成实例保留。团队任务不支持重复。

### 2.4 疲劳回顾报告

- 复用现有 `fatigue_survey`、`schedule`、`team_task_assignee`、`team_task` 表，不新增分钟分摊表。
- 新增只读聚合接口：按周 / 月返回 `surveyScoreAvg`（日终调查平均分）、`predictedScoreAvg`（模型预测平均分，可选）、峰值日、个人计划负荷、个人完成负荷、团队完成负荷、总完成负荷、`personalCompletionRate` 与疲劳趋势曲线；从本版本接口契约与前端类型中删除 `teamCompletedCount`，也不返回团队完成率。
- 疲劳趋势、预测分数与模型相关指标只使用个人日程和日终调查；团队完成负荷作为独立展示项，不参与训练。
- 报告中的个人完成率分母为周期内个人日程总数；不计算团队完成率或团队完成数，也不混入个人完成率。个人日程总数为 0 时返回 `null`（前端显示“—”），不得除零或伪造 0%。团队完成负荷直接按 `team_task_assignee.completed_at` 与 `completed_fatigue_weight` 聚合，不写入 `fatigue_daily_summary.completed_load` 或 `fatigue_survey.completed_load_snapshot`。

### 2.5 日历订阅

- 新增只读接口 `GET /api/v1/schedules/ical`，返回标准 iCal（`.ics`）格式。
- 每用户一个订阅 Token（`subscribe_token`），无需登录即可只读订阅，可随时重置。

## 六、补充决策与澄清（2026-09-07 更新）

> 本章为评审补充，对正文若干悬而未决的口径做拍板。以下决策以本条为准，正文与其冲突处按本条执行。

### 6.1 疲劳模型口径（覆盖 §1、§2.1、阶段 1）

- 个人日程仍由用户选择 1～5 级疲劳程度，算法按该用户自己的五档权重与精力上限独立适配。
- 计划负荷使用当前用户权重，完成负荷使用完成时保存的权重快照；不引入分钟换算、预计/实际投入时长或跨天分摊。
- 既有用户的疲劳档案与历史调查不做基线重算，避免无必要的历史数据跳变。

### 6.2 团队任务完成口径（覆盖 §2.2、阶段 2）

- 团队任务的待办、接受和进行中状态不计入个人计划负荷；疲劳追踪开启时当前执行人完成必须提交 1～5 级疲劳程度，追踪关闭时允许无等级完成。
- 在 `team_task_assignee` 保存 `completed_fatigue_level` 与按该用户当前权重计算的 `completed_fatigue_weight`，复用 `completed_at`。
- 多执行人分别完成、分别记录、分别按各自用户时区归入完成日；不把疲劳等级放在 `team_task` 上，不均摊、不跨天。管理员不能代替执行人填写完成等级。
- `teamCompletedLoad` 直接由该用户的执行人完成快照聚合；`totalCompletedLoad = completedLoad + teamCompletedLoad`，两者都只用于该用户完成日的展示负荷。现有 `completedLoad` 与 `completed_load_snapshot` 继续只代表个人日程。
- 团队完成负荷不进入日终调查样本、模型训练、权重/精力上限校准、疲劳预测、疲劳提醒或 AI 排程输入。
- 团队完成负荷直接按 `team_task_assignee.completed_at` 与完成权重聚合，不写入 `fatigue_daily_summary.completed_load` 或 `fatigue_survey.completed_load_snapshot`；完成率分母仍为个人日程。
- `fatigueTrackingEnabled=false` 或疲劳功能灰度关闭时，允许无等级完成团队任务，但不保存团队疲劳快照、不增加 `teamCompletedLoad`，也不要求管理员补填等级。
- 已有团队完成快照不因开关关闭而删除，关闭期间隐藏，重新开启后恢复展示；新完成在关闭期间不产生快照或团队展示负荷。重新打开或状态纠正时清除对应执行人的快照并重算受影响日期；历史团队完成记录没有快照时不批量回填默认等级。
- 管理员状态修正仅可设为 `pending`、`accepted`、`rejected`，不得代替执行人完成；整体已完成的团队任务沿用当前规则，不支持重新打开。快照不写入事件、通知、公共详情或普通管理员日志，沿用现有疲劳数据保留期限，用户删除数据时同步删除。
- 历史聚合以 `team_task_assignee.completed_at` / `completed_fatigue_weight` 为准，不因任务当前状态变化而丢失已完成执行人的记录。

### 6.3 重复任务（覆盖 §2.3）

- 重复能力仅限个人日程；实例只物化当前自然月，进入下月时按月滚动续注入。
- 每个实例继承系列的 `fatigue_level`；支持单实例 / 整个系列编辑，系列编辑只影响未来未完成实例。
- 支持排除日期（EXDATE）；排除实例不生成、不占负荷、不出现在日历中，已完成实例保留。
- 团队任务本版本不支持重复。

### 6.4 时区口径（覆盖 §2.2、§2.3、§2.4、§2.5）

- 负荷计算、完成日归属、回顾聚合、iCal 导出和重复实例均按用户时区处理。
- 周/月回顾按用户时区切分，自然周起始日固定为周一；本版本不增加可配置周起始日字段。
- 用户修改时区后，团队完成日展示按现有时区变更策略重算；已保存的完成权重快照不改变。

### 6.5 iCal 订阅范围与安全（覆盖 §2.5、阶段 6）

- 导出个人 `pending` 日程，以及分配给当前用户且处于 `pending` / `accepted` 的团队任务；不含已完成、已取消、已拒绝任务，也不含任何疲劳数据。
- 团队任务事件仅使用现有 `start_time` / `deadline_time`；在按用户隔离的订阅中使用稳定的 `team_task.id` 生成 `VEVENT UID`，不依赖执行人变更或分摊表。
- Token 使用高熵随机值，`GET /api/v1/schedules/ical?token=xxx` 访问日志对 `token` 脱敏；重置后旧链接立即失效。

### 6.6 AI 排程隐私开关（覆盖阶段 5）

- 关闭“AI 数据记录”开关后，AI 主动排程建议一并停用；建议只读取个人疲劳系数与个人负荷，不读取团队完成展示负荷作为模型输入。

### 6.7 回顾报告口径（覆盖 §2.4、阶段 4）

- 报告展示个人计划负荷、个人完成负荷、团队完成负荷和总完成负荷的分项与趋势。
- 疲劳趋势、预测分数和调查对比只使用个人日程与日终调查原始数据；团队完成负荷仅作展示，只返回 `personalCompletionRate`，不返回团队完成数、团队完成率或“预估准确度”指标。

### 6.8 个人长期任务每日进度口径（2026-09-07 已确认）

- 仅个人日程支持每日进度；跨天日程或用户主动标记的长期任务可开启，普通单日任务默认沿用一次性完成流程。
- 用户每天提交累计进度 0～100，并为本次新增进度选择 1～5 级疲劳程度；疲劳追踪关闭时可以只提交进度，不产生疲劳负荷。
- 服务端按用户时区计算本次进度增量，并以 `(schedule_id, user_id, progress_date)` 保证同日幂等；正常操作只允许累计进度增加，回退必须通过修正流程。
- 每日个人完成负荷为 `progressDelta / 100 × fatigueWeightSnapshot`，使用提交当时该用户的个性化权重快照冻结，归入该用户当天的个人完成负荷、日终调查和疲劳模型。
- 进度达到 100% 即完成任务；完成日取达到 100% 的日期，不再额外写入普通整项完成负荷，避免重复计算。未满 100% 点击完成时，必须先提交剩余进度并选择疲劳等级。
- 计划负荷仍使用任务原有计划疲劳等级，不由系统自动分摊到日期区间；每日进度是用户主动上报的实际推进，不是分钟工时记录。
- 已发生的每日进度和疲劳历史在暂停、延期、取消时保留；历史修正、重新打开或删除进度时重算受影响日期及个人训练数据。
- 团队任务不采用每日进度，不在认领时或执行过程中结算疲劳；仍由当前执行人在最终完成时选择疲劳等级，仅计入完成日展示负荷。
- 实现约定（2026-09-13 落地时确定，详见 §7.3）：同日多次提交只保留该日累计增量并重算一次负荷；`PUT /progress/{date}` 的 `progressDelta` 是该日增量的绝对值，传 0 即删除该日记录。

### 7.3 实现约定与人工复核项

1. **每日进度的两个约定**（实现时确定，如需调整请回写本章）：
   - 同日多次提交时，`schedule_progress_daily.progress_delta` 记录**该日累计增量**（例如先提交 40% 再提交到 70%，该日存 70%），当日负荷按该值重算一次，因此同日幂等且不重复累计。
   - `PUT /progress/{date}` 的 `progressDelta` 是**该日增量的绝对值**（不是增量差值）；传 0 表示删除该日记录。修正后按日期顺序重算累计值，累计回退到不足 100% 时任务自动重新打开。
2. **关闭每日进度的前置条件**：任务存在进度记录时不允许关闭 `progressTrackingEnabled`，必须先通过修正把记录清零，避免关闭后用普通完成流程重复计入负荷。点击事件类型与每日进度互斥：切到「安排事项」前也要先取消勾选（后端会以 “only available for tasks” 拒绝）。
3. **编辑已有进度任务**：调用方必须把 `progressTrackingEnabled` 原值回传；未回传时服务端沿用当前值（有 `ScheduleProgressTests.editingProgressScheduleKeepsTrackingAndHistory` 覆盖），账户端编辑弹窗已按此回填，避免把编辑操作误判为「关闭每日进度」。
4. **视口与控制台复核（2026-09-20 已完成）**：浏览器实测 375px 下 12 个路由（首页/日历/列表/详情/团队/任务/通知/调查/回顾/提醒/我的/设置）、1280px 下 6 个关键页面，横向溢出均为 0，控制台无错误无警告；进度记录表在 640px 以下转纵向卡片，并保留 `overflow-x: auto` 兜底。
