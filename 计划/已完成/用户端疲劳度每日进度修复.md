# 用户端疲劳度每日进度修复计划

> 编写日期：2026-09-20
> 状态：已实施完成（P01–P11 全部落地并通过后端/前端自动化与浏览器实测；唯一遗留为桌面端 Tauri 实机视觉复核，见 §十一）
> 完成日期：2026-09-20
> 关联计划：`计划/用户端计划v2.1-2.md` 第 6.8、7.3 节
> 适用范围：用户网页端、复用用户页面的桌面工作台，以及每日进度所需的后端和数据库配套
> 修复目标：在不改变“用户选择疲劳等级、算法按用户独立适配”这一核心口径的前提下，补齐长期任务每日进度的并发一致性、历史补录、状态流转、负荷展示和周期完成率闭环

---

## 一、背景与当前结论

个人长期任务每日进度已经完成初步实现，当前链路包括：

1. 用户开启每日进度模式。
2. 用户提交 0～100 的累计进度。
3. 服务端根据上一次累计进度计算本次正向增量。
4. 用户为本次推进选择 1～5 级疲劳程度。
5. 服务端按用户当时的个性化权重计算当天完成负荷并冻结快照。
6. 累计进度达到 100% 后自动完成任务。
7. 每日负荷进入个人日汇总、日终调查、疲劳模型和周/月回顾。

核心设计方向正确，但代码复核发现以下问题仍未闭合：

- 并发提交可能覆盖彼此的累计进度，产生“状态已完成但进度不足 100%”的数据矛盾。
- 历史修正达到 100% 时，完成日可能被写成修正当天，而不是用户实际补录的进度日期。
- 疲劳追踪关闭时，网页仍可能把默认疲劳等级发送给后端，导致纯进度提交失败。
- 列表和桌面快捷入口仍调用普通完成接口，绕过每日进度流程。
- 只有部分进度的日期不会触发日终调查入口。
- 已完成列表可能把进度任务显示成整项任务的完整负荷。
- 桌面快捷时间轴不能完整创建、查看和提交每日进度。
- 历史修正界面不能补录没有已有记录的日期。
- 现有完成率按“计划日分母、完成日分子”统计，跨周期时可能超过 100%。
- 进度历史表在 375px 视口存在横向溢出风险。

本计划只处理上述每日进度及其直接关联问题，不重新改动重复日程、团队历史、iCal、AI 或安全模块的其他已知问题。

## 二、已确定的业务口径

### 2.1 每日进度与疲劳

- 每日进度仍采用累计百分比，取值范围为 0～100。
- 普通提交只能增加累计进度；回退、删除和历史补录走历史修正接口。
- `PUT /schedules/{id}/progress/{date}` 中的 `progressDelta` 继续表示该日增量的绝对值，传 `0` 表示删除该日记录。
- 同一任务同一天重复提交，只保留该日累计增量并重算一次负荷；后一次提交的疲劳等级作为该日最终等级。这是当前计划已经确认的约定。
- 疲劳追踪开启时，当日增量大于 0 必须提交 1～5 级疲劳等级；关闭时只保存进度，不发送疲劳等级、不保存疲劳快照、不产生完成负荷。
- 每日完成负荷继续使用：

  `当日增量 ÷ 100 × 提交时的用户个性化权重`

- 进度达到 100% 后自动完成任务，不再额外写入普通整项完成负荷。

### 2.2 历史补录规则

用户确认允许补录没有现有记录的历史日期。补录规则如下：

- 允许补录今天以前的日期，不允许补录未来日期。
- 补录日期不得早于任务在用户时区下的有效起始日期：优先使用任务开始日期；没有开始日期的截止任务使用任务创建日期。
- 不以任务结束日期作为硬上限，允许对逾期任务补录结束日期之后实际发生的推进。
- 补录日期受现有疲劳数据保留期限制，沿用 `retentionDays`，不新增另一套保留期限。
- 补录后按日期顺序重算该任务所有后续记录的 `cumulative_progress`。
- 若补录使累计进度首次达到 100%，以达到 100% 的那条进度记录日期作为任务完成日。
- 若删除或修正历史记录使累计进度低于 100%，任务重新进入待处理状态；已产生的每日疲劳记录按受影响日期重新计算。

### 2.3 “接受后完成”和“取消后完成”的状态口径

#### 团队任务

- `accepted -> completed` 是合法状态转换。接受表示当前执行人承担任务，完成是执行后的下一步，因此接受后可以完成是正常行为。
- `pending`、`rejected`、`cancelled` 不允许直接完成。
- 被取消的团队任务必须先由允许的恢复流程恢复，再重新分配或接受，之后才可以完成。
- 完成接口必须在事务内再次校验当前执行人状态，不能只依赖前端按钮是否显示。

#### 个人每日进度任务

- 新增进度和自动完成只允许发生在 `pending` 状态。
- `cancelled` 状态不能直接通过普通完成接口或进度提交接口完成，必须先恢复为 `pending`。
- 取消任务后可以查看和修正已经发生的历史记录，但修正不能直接把取消状态改成完成；若累计达到 100%，保持取消状态，恢复后再由系统确认完成。
- 普通已完成任务的“恢复”仍然保留；恢复不会删除每日进度历史，只会清除整项完成状态，之后可通过修正或 100% 提交重新完成。

### 2.4 完成率不得超过 100%

完成率必须由同一批任务计算，不能继续使用互相独立的“周期内计划任务数”和“周期内完成任务数”。

采用以下口径：

1. 构造周期任务集合 `eligibleTaskIds`，集合包括：
   - 计划日期落在本周期内的个人任务。
   - 周期开始前已经存在、周期开始时仍未完成、并在本周期内继续承接的任务。
   - 计划日期在周期外但最终在本周期完成的任务，作为跨周期结转任务纳入集合。
2. 排除没有任何完成记录、且在周期开始前已经取消并未恢复的任务。
3. 每个任务 ID 只出现一次。
4. 分子为 `eligibleTaskIds` 中最终完成日期落在本周期内的任务数。
5. 分母为 `eligibleTaskIds` 的任务数。
6. `personalCompletionRate = 分子 ÷ 分母`；分母为 0 时返回 `null`。
7. 服务端增加断言和日志：如果分子大于分母，记录数据异常并阻止异常值进入接口；不能只用 `min(rate, 1)` 静默掩盖统计问题。

长期任务只有累计进度达到 100% 才进入完成率分子。40%、70% 等每日推进只进入个人完成负荷，不算完成项。

这样跨周、跨月完成的任务会被纳入同一任务集合，分子天然是分母的子集，完成率不会超过 100%。

### 2.5 进度任务的完成日期与完成时间

历史补录只知道“哪一天达到 100%”，不一定知道真实完成时刻。为避免继续把修正操作时间误当成完成日，推荐新增：

- `schedule.progress_completed_date DATE NULL`：仅每日进度任务使用，保存首次达到 100% 的用户时区日期。
- `completed_at` 继续保存实际提交或修正操作的时间戳，普通一次性任务逻辑不变。
- 报告、日汇总和用户端完成日期展示，进度任务优先使用 `progress_completed_date`。
- 已有进度任务迁移时：优先从每日记录中找到累计首次达到 100% 的日期；无法推导时，使用现有 `completed_at` 按用户时区转换的日期作为兼容回填值。

如果实施阶段决定不新增字段，必须至少统一一个可重建的完成日期来源，不能继续只使用当前修正时间。

## 四、后端与数据库实施方案

### 4.1 并发提交与事务一致性

修改 `ScheduleService.submitScheduleProgress`：

1. 在事务最早阶段使用 `SELECT ... FOR UPDATE` 锁定当前用户的 `schedule` 行。
2. 锁定后重新读取 `status`、`progress_percent` 和 `progress_tracking_enabled`，禁止使用事务外的旧对象。
3. 根据数据库中的最新累计进度计算本次增量。
4. 对当天的 `schedule_progress_daily` 记录执行锁定式查询；存在则更新，不存在则插入。
5. 在同一事务内更新任务累计进度、进度完成日期、状态和提醒状态。
6. 只有锁内确认累计进度达到 100% 时，才允许写入完成状态。
7. 事务提交前重新检查：
   - `progress_percent` 与每日增量总和一致。
   - `status='completed'` 时累计进度必须为 100%。
   - 进度任务不能出现整项完成疲劳快照。

唯一约束仍保留，作为第二层保护，但不能把唯一约束冲突重试当作并发一致性方案。

### 4.2 历史修正与累计重建

修改 `correctScheduleProgress`：

- 接受已有日期修改，也接受没有记录日期的补录。
- 删除目标日期后，按日期顺序重新计算所有剩余记录的累计进度。
- 计算“首次达到 100% 的日期”，写入 `progress_completed_date`。
- 任务原本已完成但完成日期发生变化时，更新进度完成日期并重算原日期、新日期和所有受影响进度日期。
- 任务累计低于 100% 时，清除整项完成字段并恢复待处理状态；保留每日进度记录。
- 取消状态下不自动改成完成，必须先恢复任务，再由 100% 进度完成。
- 所有受影响日期都要触发个人日汇总重算，并使对应日终调查样本失效后重新校准。

### 4.3 疲劳追踪关闭时的接口契约

后端继续保持严格规则：

- 追踪开启且增量大于 0：`fatigueLevel` 必填且只能为 1～5。
- 追踪关闭：请求体不得携带 `fatigueLevel`，只保存进度，负荷为 0。
- 追踪关闭时如仍收到等级，返回明确 400 错误。

前端和 Pinia 请求封装必须只在 `fatigueTrackingEnabled === true` 且增量大于 0 时写入 `fatigueLevel`。

### 4.4 任务状态机防护

个人任务和团队任务分别增加后端状态断言：

- 个人每日进度提交：仅 `pending`。
- 个人普通完成：进度任务一律拒绝；非进度任务沿用普通流程。
- 个人取消任务：保留已产生的进度负荷，但不能继续提交新进度或自动完成。
- 团队完成：仅当前用户执行人状态为 `accepted` 时允许；锁定执行人记录后再写入完成时间和疲劳快照。
- 团队 `cancelled`、`rejected`、`pending` 状态不能完成。
- 前端只负责隐藏不适用按钮，最终校验必须在后端完成。

### 4.5 日终调查触发口径

以下位置统一改为使用“个人完成负荷是否大于 0”判断是否有调查资格：

- `surveyToday` 默认日期选择。
- `availableDates` 日期列表。
- `surveyPending`。
- `scanSurveyPrompts` 定时提醒。

注意：

- `completedCount` 仍可继续表示完整完成的任务数量，用于界面统计。
- 团队完成负荷不参与日终调查触发。
- 追踪关闭时进度负荷为 0，不触发疲劳调查。

### 4.6 列表和分组负荷聚合

修改列表摘要计算：

- 进度任务的完成负荷使用 `schedule_progress_daily.completed_load` 按任务聚合。
- 普通任务继续使用 `completed_fatigue_weight` 快照。
- 避免按每条任务单独查询，采用当前列表任务 ID 批量聚合，避免 N+1 查询。
- 接口可为进度任务补充 `progressCompletedLoad`，前端明确显示“进度累计完成负荷”。
- 不把进度任务再次回退到计划疲劳权重。

### 4.7 完成率聚合

新增一个独立的任务集合构建方法，避免分子、分母分别用不同 SQL：

1. 以用户时区计算计划日、周期开始和周期结束。
2. 构造计划任务、周期开始前结转任务、周期内完成任务的 ID 并集。
3. 过滤删除任务、无完成记录且在周期开始前已取消的任务。
4. 以唯一 ID 集合计算分母。
5. 从同一集合中筛选最终完成日在周期内的任务计算分子。
6. 进度任务使用 `progress_completed_date`，普通任务使用 `completed_at` 转换后的本地日期。
7. 增加断言、监控日志和测试，禁止向前端返回大于 1 的比例。

## 五、用户端实施方案

### 5.1 详情页每日进度

- 关闭疲劳追踪时不渲染疲劳选择器，并且请求体不带等级字段。
- 增加“补录历史日期”按钮。
- 补录弹窗包含：日期、当日增量、疲劳程度、当前累计进度预览、影响日期提示。
- 日期选择器默认限制为任务有效起始日期至今天。
- 追踪开启时，增量大于 0 必须主动选择疲劳等级。
- 保存前显示累计进度变化；达到 100% 时明确提示任务将完成。
- 取消任务的详情页不显示可直接完成或提交新进度的按钮，显示“恢复任务后继续”。
- 完成日期显示使用进度完成日期，不直接把修正操作时间当作完成日。

### 5.2 列表和首页入口

- 进度任务的“完成”按钮改为打开进度提交弹窗或跳转详情页。
- 不再让进度任务调用普通 `/complete` 接口。
- 普通一次性任务继续沿用当前快速完成流程。
- 列表状态菜单、右键菜单、首页快捷按钮保持同一判断逻辑，避免入口不一致。
- 完成列表显示实际进度累计负荷，普通任务显示整项完成快照负荷。

### 5.3 桌面快捷时间轴

优先复用用户端详情页或抽取共用进度组件，避免桌面端重新实现一套规则：

- 快捷新建编辑器增加每日进度开关，条件与网页端一致：仅截止任务、时间段任务且非重复任务可开启。
- 快捷详情加载 `/schedules/{id}/progress`，展示进度条、每日记录和补录入口。
- 快捷“完成”按钮对进度任务打开剩余进度提交，不调用普通完成接口。
- 已取消进度任务只显示恢复操作。
- 快捷时间轴历史负荷使用进度累计负荷。

### 5.4 日终调查入口

- 当天只有部分进度但 `completedLoad > 0` 时，也显示调查提醒和调查日期。
- 调查页面明确区分“已完成任务数”和“个人完成负荷”，避免用户误以为必须整项完成才有调查。

### 5.5 移动端布局

二选一，优先采用响应式记录卡片：

- 375px 以下将六列历史表转为每条记录的纵向卡片；或
- 保留表格但外层增加 `overflow-x: auto`，并设置最小宽度和可见操作列。

验收时必须覆盖 375px、390px、768px 和桌面宽度，不得出现页面整体横向滚动。

### 5.6 进度状态加载保护

- 切换任务前清空旧的 `scheduleProgress`。
- 每次加载生成请求序号，旧请求返回时不得覆盖当前任务数据。
- 加载失败时明确显示错误状态，不继续展示上一任务的历史记录。

## 六、接口与数据契约调整

### 6.1 进度查询响应

在保持现有字段兼容的基础上，补充：

- `completedDate`：进度任务首次达到 100% 的用户时区日期。
- `canSubmitProgress`：当前状态是否允许提交新进度。
- `canBackfill`：当前用户是否允许补录历史日期。
- `backfillMinDate`、`backfillMaxDate`：前端日期选择范围。
- `totalCompletedLoad`：所有每日记录的累计个人完成负荷。

### 6.2 历史修正接口

继续使用：

`PUT /api/v1/schedules/{id}/progress/{date}`

请求体：

```json
{
  "progressDelta": 40,
  "fatigueLevel": 4
}
```

约束：

- `progressDelta` 是目标日期的绝对增量。
- `progressDelta=0` 删除目标日期记录。
- 追踪开启且增量大于 0 时必须有 `fatigueLevel`。
- 日期不能是未来，不能超出补录下限和保留期限。
- 取消任务不能因历史修正自动转为完成。

### 6.3 报告响应

保留现有报告字段，并明确：

- `personalCompletionRate` 范围只能是 `0～1` 或 `null`。
- `personalCompletedCount` 和 `personalScheduleCount` 使用同一任务集合。

## 八、测试计划

### 8.1 后端必测场景

- 两个并发请求同时提交 50% 和 100%，最终进度、状态和每日记录一致。
- 同日先提交 40% 再提交 70%，只保留一条记录，负荷按 70% 重算一次。
- 历史补录不存在的日期，累计值按日期顺序重建。
- 历史修正使任务首次达到 100%，完成日为目标进度日期。
- 已完成任务修改 100% 日期，完成日同步更新。
- 删除历史记录使进度低于 100%，任务恢复待处理。
- 取消任务后提交新进度、普通完成和自动完成均被拒绝。
- 团队任务 `accepted -> completed` 成功，`cancelled -> completed` 被拒绝。
- 关闭疲劳追踪时提交进度不带等级，负荷为 0。
- 追踪开启时缺少等级、等级越界、非整数均返回 400。
- 只有部分进度时可以进入日终调查，团队负荷不能触发调查。
- 进度任务列表完成负荷等于每日记录之和，不等于整项计划权重回退值。
- 跨周和跨月完成率不超过 100%，跨周期结转任务只计算一次。
- 用户时区为 UTC+14、UTC-10 时，进度日期和完成日分别正确。
- 删除任务、恢复任务、修改时区后，相关日期摘要和训练样本正确重算。

### 8.2 前端必测场景

- 疲劳追踪关闭时网络请求体不包含 `fatigueLevel`。
- 进度任务在列表、首页、右键菜单和桌面端点击“完成”都进入进度流程。
- 取消任务不显示直接完成按钮。
- 补录日期可以新增记录，并正确显示累计进度。
- 加载任务 B 失败时不会显示任务 A 的进度历史。
- 桌面快捷编辑器可以创建进度任务，快捷详情可以提交和修正。
- 375px、390px、768px 和桌面宽度无页面整体横向溢出。
- 关键页面无控制台错误，重复点击不会发送重复提交。

### 8.3 数据库和迁移测试

- V28 或等价迁移在空库和已有 V27 数据上均可执行。
- 已有完成进度任务可以正确回填完成日期。
- 唯一约束、检查约束和索引保持有效。
- 迁移失败时事务可回滚，不产生半完成结构。

## 九、验收标准

### 数据一致性

- 任何并发提交后，任务状态为 `completed` 的前提是累计进度严格等于 100%。
- 每日记录累计值按日期递增，任务累计进度与每日记录总和一致。
- 历史修正不会把完成日错误记录为修正操作当天。

### 状态规则

- 团队任务接受后可以完成，这是合法状态转换。
- 取消或拒绝状态不能直接完成，必须先恢复并重新接受。
- 个人取消进度任务不能直接提交新进度或自动完成。

### 疲劳与调查

- 关闭追踪时只记录进度，不保存疲劳等级、权重快照和负荷。
- 部分进度只要产生个人完成负荷，就能进入日终调查流程。
- 团队完成负荷不进入个人日终调查和模型训练。

### 报告与展示

- 进度任务列表显示每日负荷累计值。
- 个人完成率始终处于 0%～100%，无任务时显示“—”。
- 长任务跨周期完成不会造成完成率超过 100%。
- 网页端、桌面端、首页、列表、详情、疲劳报告使用同一进度和负荷口径。

### 兼容性

- 普通一次性个人任务不改变原有完成流程。
- 团队任务不引入每日进度模型。
- 已有历史疲劳快照和非进度任务数据不被重新解释。

## 十、实施约束与风险

- 不用简单截断比例来掩盖完成率统计错误。
- 不通过前端隐藏按钮代替后端状态校验。
- 不在每次列表渲染中对每个任务单独查询每日记录。
- 不把每日进度自动拆成系统推测的工时或分钟数。
- 历史补录会触发多个日期重算和训练样本失效，需要限制在现有保留期内并记录操作日志。
- 新增完成日期字段时需要同步更新详情、列表、首页、报告、导出和测试数据结构。
- 如果不新增字段而选择从每日表实时推导完成日，必须覆盖删除、回退、重复修正和迁移回填场景。

实施后的两点口径说明（供后续核对）：

- **完成率集合口径**：分子分母统一取自「计划日落在本期」∪「完成日落在本期」的同一任务 ID 集合（长期任务以 `progress_completed_date` 判定完成，普通任务用 `completed_at` 转换的用户时区日期）。第二项刻意只纳入「本期完成」的跨周期任务，不纳入「期初未完成且本期仍挂起」的任务，否则分母会随挂起任务不断膨胀且随完成时间变动，报告结果不稳定；此选择同时保证分子恒为分母子集，完成率不会超过 100%。
- **取消任务的进度负荷**：取消保留已经发生的每日进度负荷与历史记录，历史修正也不会把取消状态改成完成，必须先恢复为待处理再由 100% 进度完成。

浏览器实测中发现并修复的界面缺陷（已包含在上表的 web-user 与类型检查结论中）：

- **取消态吞掉了进度记录表**：面板里「任务已取消」提示与记录表写在同一个 `v-if / v-else-if` 链上，导致取消任务只能看到提示、看不到逐日记录，与「取消后仍可查看和修正历史」冲突。已改为互不依赖的条件。
- **弹窗里的开关排版错位**：`.modal-panel label` 的 `display: grid` 覆盖了开关的 `display: flex`，勾选框与文案上下堆叠。已在 `style.css` 用更高优先级选择器修正为同行。
- **面板布局样式整块失效（fragment 根节点）**：`ScheduleProgressPanel` 有多个根节点，调用方传的 `class`（网页 `.detail-progress-panel`、桌面 `.quick-detail-progress`）被 Vue 丢弃并刷警告，面板顶部间距恒为 0、贴在上一个区块上。已改为 `inheritAttrs: false` + 把 `attrs.class` 显式绑到面板根节点，网页侧再用 `:deep()` 命中；修复后 `margin-top` 生效、控制台警告清零。
- **「待办 + 累计 100%」没有完成入口**：取消后恢复、或修正回退再补回时，任务会停在待办且累计 100%，此时「完成剩余进度」因 `percent < 100` 被隐藏，用户没有任何显式完成按钮（只有点「提交进度」重填 100% 才能完成）。已抽出 `progressCompletionActionLabel` / `progressSubmitDialogTitle`（网页与桌面共用，附单测），该状态下主按钮变为「标记完成」、弹窗标题变为「标记任务完成」并说明本次不产生新负荷。
- **并发用例断言过严（测试侧）**：P01 加行锁后，并发提交「50 与 100」时后到的一笔会在锁内重读状态、得到 `completed` 并以 `schedule must be pending` 拒绝，比原先预期的 `progress cannot decrease` 更准确。测试已放宽为接受两种合法业务拒绝，连跑 3 次稳定通过。
