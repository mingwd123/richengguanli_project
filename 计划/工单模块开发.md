# 工单模块开发计划

> 编写日期：2026-09-20
> 状态：待实施，本文不表示功能已经完成
> 适用范围：用户网页端、复用用户页面的桌面工作台、管理端及后端配套
> 目标：提供可由管理员临时开放的公开问题反馈大厅，集中收集测试问题、公开处理进展、减少重复提交。

## 一、需求与范围

### 1.1 已确认需求

1. 用户端新增工单模块，收集项目使用中的问题和建议。
2. 工单公开，其他用户可查看问题、回复、截图和处理结果。
3. 管理端可以开启或关闭模块；关闭后用户端不显示入口，也不能继续访问模块。
4. 截图每张最大 10MB。
5. 当前服务对象为测试用户，不做私密工单、匿名模式或复杂隐私设置。

### 1.2 本计划的公开范围

- “所有人可见”按项目现有账号体系落地为：所有已登录且有效的测试用户均可查看，不限工单提交者、团队或执行人。
- 不新增未登录访客入口，不向搜索引擎开放；若未来需要互联网匿名访问，应单独扩展读取和限流策略。
- 所有用户提交的标题、描述、复现步骤、公开回复和截图均公开；显示提交者昵称，不显示邮箱、手机号和账号凭据。
- 管理员内部备注、操作日志、限流信息和安全凭据不是工单公开内容，不进入公开响应。
- 页面填写区显示简短提示：“工单内容和截图将对所有测试用户公开。”
- 不做自动隐私识别或复杂审核流程，但仍保留身份鉴权、附件校验、脚本注入防护和管理员隐藏违规内容的能力。

### 1.3 首版包含

- 公开工单大厅、搜索筛选、详情与讨论。
- 我的提交、我的关注、我也遇到。
- 创建工单、图片附件、回复补充、处理状态时间线。
- 管理端处理、内部备注、优先级、置顶、重复工单合并。
- 站内通知及功能开关。
- 网页端、桌面工作台和移动浏览器适配。

### 1.4 首版不做

- 私密工单、匿名提交、邮件客服和实时聊天。
- 自动 AI 回复、自动判重和自动合并。
- SLA、复杂分派规则、客服排班、计费。
- 视频、压缩包、日志文件及其他任意附件上传。
- 桌面快捷时间轴内重建一套工单系统；桌面端通过完整工作台访问复用页面。

## 二、公开大厅与减少重复提交

### 2.1 入口与页面

- 用户端导航显示“工单”，页面标题为“问题反馈”。
- 桌面端完整工作台提供相同入口，移动端放入现有更多导航。
- 大厅默认展示全部公开工单，不仅展示当前用户提交的工单。
- 顶部提供搜索框、“提交工单”按钮，以及“全部 / 我的提交 / 我的关注”视图。
- 展示工单编号、标题、类型、所属模块、状态、提交者昵称、更新时间、回复数和“我也遇到”人数。
- 默认按最后活动时间排序，可切换最新提交和最多遇到；置顶工单在各自筛选结果中优先展示。
- 筛选支持状态、问题类型、所属模块；管理端另支持提交者、处理人、优先级和日期范围。
- 列表分页，默认每页 20 条，服务端限制单页上限 100 条。
- 已解决和已关闭问题仍可搜索，帮助用户找到已有解决方法。

### 2.2 提交前查重

1. 用户填写标题后，防抖查询可能相关的公开工单，至少支持标题关键词匹配。
2. 显示最多 5 条相似结果，包含状态、标题和“查看”操作。
3. 用户可以打开已有工单并点击“我也遇到”，无需再创建一条。
4. 查重仅提示，不强制阻止提交，也不能因搜索失败丢失表单。
5. 不以相同标题直接判断重复；最终是否合并由管理员确认。

### 2.3 “我也遇到”与关注

- “我也遇到”表示同样遭遇该问题，每个用户每张工单最多一条，可取消。
- 首次点击时自动关注；取消“我也遇到”不自动取消关注，两种行为分别管理。
- “关注”仅表示订阅处理进展，所有用户都可以单独关注或取消。
- 工单作者创建成功后默认关注，但允许取消关注。
- 计数在服务端维护或聚合，使用唯一约束和幂等接口避免重复增加。
- 不展示遇到者的完整用户列表，首版展示总人数即可。

## 三、工单内容与填写规则

| 字段 | 规则 |
|------|------|
| 工单编号 | 服务端生成唯一编号，例如 `TK-00001234`，只作展示和查找，不作为权限凭据 |
| 标题 | 必填，去除首尾空格后 5～100 字 |
| 问题类型 | 功能异常、显示问题、数据问题、账号问题、使用咨询、功能建议、其他 |
| 所属模块 | 日程、团队任务、每日进度、疲劳评估、通知提醒、AI、账号与设置、桌面端、其他 |
| 问题描述 | 必填，10～5000 字 |
| 复现步骤 | 选填，最多 2000 字 |
| 预期结果 | 选填，最多 1000 字 |
| 截图 | 初始提交最多 5 张，每张不超过 10MB |
| 使用环境 | 客户端类型、应用版本、浏览器、操作系统；用户可预览和修改 |
| 发生页面 | 选填，仅保存站内路径，去除查询参数和 URL fragment |
| 处理优先级 | 管理员设置，用户不填写；低、普通、高、紧急，默认普通 |
| 处理人 | 可空，由管理员认领或指定有效管理员 |
| 解决摘要 | 标记已解决时必填，10～2000 字 |
| 修复版本 | 可选，由管理员填写实际已发布版本，不自动承诺发布时间 |

补充说明：

- 不自动读取用户的任务正文、控制台日志、Token 或完整请求内容。
- 文本先采用纯文本安全渲染，保留换行；不支持原始 HTML。
- 管理员设置的优先级、内部处理人信息可仅在管理端显示；公开详情展示状态、公开回复、解决摘要和修复版本。
- 不允许用户提交服务器管理字段，例如作者 ID、状态、置顶、优先级和管理员消息类型。

## 四、回复与处理流程

### 4.1 状态

| 状态 | 含义 | 常见下一步 |
|------|------|------------|
| 待处理 `open` | 新提交，等待管理员查看 | 处理中、待补充、已解决、已关闭 |
| 处理中 `in_progress` | 管理员正在排查 | 待补充、已解决、已关闭 |
| 待补充 `waiting_reporter` | 等待原提交者补充材料 | 处理中、已解决、已关闭 |
| 已解决 `resolved` | 已提供解决办法，等待确认 | 已关闭、处理中 |
| 已关闭 `closed` | 处理结束、撤回、重复或其他明确原因 | 经允许重新进入处理中 |

### 4.2 用户操作

- 所有有效用户都可在未关闭的公开工单下回复，补充自己的复现情况；回复最多 3000 字，每条最多 5 张截图。
- 原提交者在“待补充”状态回复后，自动回到“处理中”；其他用户回复不改变状态。
- 原提交者可对“已解决”点击“确认解决”，转为“已关闭”。
- 原提交者可对“已解决”选择“仍未解决”，必须填写原因，转回“处理中”。
- 原提交者可撤回自己的未关闭工单，关闭原因为“用户撤回”；记录保持公开，不物理删除。
- 作者可对因“已解决”或“用户撤回”关闭的工单申请重新处理，填写原因后转为“处理中”。
- 重复、违规、无效等管理关闭不允许用户直接重开；可在目标主工单补充或新建有依据的反馈。
- 已关闭工单不允许普通回复，先执行允许的重新处理操作；仍可查看、关注和标记“我也遇到”。
- 首版提交后不提供任意改写原文功能，错误信息通过追加回复纠正，保留排查上下文。

### 4.3 管理员操作

- 回复、认领、转交处理人、设置优先级、置顶及取消置顶。
- 改为“待补充”时必须给出需要补充的信息。
- 改为“已解决”时必须填写公开解决摘要，可填写修复版本。
- 关闭工单时必须选原因：已解决、重复问题、用户撤回、信息不足、暂不支持、违规或无效内容、其他。
- 对非重复工单允许重新打开，必须记录原因。
- 重复工单通过专门“取消合并”恢复，不能绕过合并关系直接重开。
- 内部备注与公开回复必须有清晰区分，默认发送公开回复；内部备注不产生用户通知。
- 首版不自动按时间关闭工单，不自动将新回复解释为已经解决。

### 4.4 状态一致性

- 后端统一校验状态转换、操作者权限、必填原因及工单当前版本。
- 状态修改、事件写入和通知事件入队在同一事务内完成。
- 管理端使用版本号或等价并发校验，避免两位管理员覆盖彼此处理结果；冲突返回 409 并提示刷新。
- 重复请求不得重复回复、关闭或发送通知。
- 状态时间线仅公开必要动作，不暴露内部备注、操作 IP 或安全日志。

## 五、重复工单合并

### 5.1 合并行为

1. 管理员选择一张正常可见、非重复的工单作为主工单。
2. 源工单标记已关闭，关闭原因为重复，并保存 `duplicate_of_id`。
3. 源工单保留原文、截图和回复，不复制到主工单，避免作者和时间混乱。
4. 源详情显著显示“该问题已合并至 TK-xxx”，可跳转主工单。
5. 源工单作者和关注者以去重方式关注主工单；源工单历史关注记录保留。
6. “我也遇到”人数不简单相加；首版各工单独立计数，源详情引导用户在主工单标记。
7. 主工单状态变化通知合并后的关注者，同一事件同一用户最多通知一次。

### 5.2 校验与撤销

- 禁止合并自身、循环合并、合并到隐藏或已被合并的工单。
- 首版禁止将已经接收其他重复工单的主工单再次合并，避免嵌套关系。
- 合并不受源工单是否已有回复限制，但必须填写合并说明。
- 管理员可取消合并，源工单回到“待处理”，保留操作事件。
- 取消合并不自动撤销已经建立的主工单关注，避免误删用户之后主动建立的订阅。

## 六、截图与附件

### 6.1 规格

- 每张图片最大 `10 × 1024 × 1024` 字节，即 10MiB，界面统一标为 10MB。
- 支持 JPEG、PNG、WebP；首版不支持 SVG、GIF、HTML 和其他文件。
- 每张工单初始内容最多 5 张，每条回复最多 5 张。
- 单次上传 1 张，表单可分批上传；前端显示进度、失败重试和移除。
- 限制图片解码像素总量，例如不超过 4000 万像素，避免小文件高解压内存消耗。
- 管理端和用户端均提供缩略图和点击放大，原图查看仍需鉴权。

### 6.2 上传与关联

- 使用服务端生成的随机存储键，不能把客户端文件名作为磁盘路径。
- 同时检查扩展名、文件内容签名和图片是否可解码；不能只信任 MIME 声明。
- 上传后形成临时附件，只能由上传者关联到自己本次创建的工单或回复。
- 提交事务内校验附件归属、数量、有效期、未绑定状态，再绑定附件。
- 提交前临时附件仅上传者和管理员可读；绑定公开内容后所有已登录测试用户可读。
- 附件受工单可见性和功能开关约束，不能提供绕过鉴权的永久公共地址。
- 未关联附件 24 小时后清理；上传接口和清理任务必须防止误删刚被绑定的图片。
- 隐藏工单或回复时，其图片同时对用户不可见；管理端仍可查看。
- 功能关闭不删除附件和工单历史。
- 联调检查后端 multipart 限制和实际反向代理上传限制，均需覆盖 10MB 图片及请求额外开销。

## 七、管理端开关

### 7.1 设置与权限

- 管理端“工单管理”提供功能设置，使用数据库持久化 `enabled`，默认关闭。
- 超级管理员可以开启和关闭；普通有效管理员可以处理工单，但不能切换全局开关。
- 沿用现有管理员身份和超级管理员权限判断，不另造一套角色系统。
- 切换开关记录操作者、变更前后值、时间和操作日志。
- 开启后无需重启后端或重新发布前端。
- 关闭前显示待处理、处理中、待补充数量，二次确认历史数据仍保留。

### 7.2 关闭后的行为

| 对象 | 处理方式 |
|------|----------|
| 用户导航 | 隐藏工单入口 |
| 公开大厅、详情、搜索 | 不再提供用户访问 |
| 提交、回复、关注、我也遇到 | 后端拒绝操作 |
| 用户附件上传与读取 | 同样拒绝，不能靠旧图片地址继续读取 |
| 已打开页面 | 下一次配置刷新或请求返回关闭错误时退出到首页，清空工单页面缓存 |
| 用户工单通知 | 暂停新增投递，已有工单通知在列表和未读数中隐藏 |
| 管理端 | 始终可查看历史、回复、设置状态和重新开启 |
| 已有数据 | 不删除，再开启后恢复可见 |

### 7.3 实时性与竞态

- 登录后、页面导航、窗口重新聚焦时刷新功能配置；在线期间最多每 60 秒刷新一次。
- 服务端用户工单接口始终检查数据库配置，不能只依赖本地缓存或前端菜单。
- 配置加载失败时隐藏入口，不将无法确认的状态视为开启；提示重试而不是误报“没有工单”。
- 使用统一业务错误码 `TICKET_FEATURE_DISABLED`，前端集中处理。
- 写入事务在持久化前检查开关，并与关闭操作按固定锁顺序协调；关闭事务完成后，新用户写入必须被拒绝。
- 关闭前已合法提交的数据保留，不回滚已经成功的工单。
- 关闭不能撤回用户已经看到或下载的内容；服务器只能停止后续访问。
- 不承诺已经发出的网络响应能被撤回。
- 同一数据库事务中协调开关锁和工单锁，避免反向加锁造成死锁。

## 八、通知规则

- 作者和关注者接收管理员公开回复、状态变化、合并等重要进展通知。
- 其他用户普通讨论不向所有关注者逐条推送，避免公开大厅形成通知噪声；管理端更新未读活动标记。
- 当前操作人不接收自己的操作通知。
- 通知只显示工单编号、简短标题和事件类型，不复制完整描述或图片。
- 工单提交成功后用户自动关注，通知投递失败不得使创建结果变成失败。
- 复用现有通知展示和跳转能力，新增明确工单类型与目标 ID。
- 通知事件建议使用事务内事件表和后台投递，唯一键按“事件 ID + 接收者 ID”去重；先检查现有通知设施是否已有等价能力。
- 投递时再次检查模块开关、接收者有效性、关注状态和工单可见性。
- 关闭期间产生的事件保留，但标记为抑制投递，再开启不集中补发历史通知。
- 关闭前尚未投递的事件在关闭时抑制，避免重新开启后突然补发。
- 重新开启后，旧通知恢复展示并保持原已读状态；隐藏工单对应通知不恢复用户可见。
- 管理端展示新工单数和新回复数；已有全局管理员通知机制可复用，否则首版使用列表标记和定时刷新。

## 九、数据结构建议

所有结构通过新的 Flyway 迁移创建，版本号以实施时仓库最新版本为准，不修改已执行迁移。

| 表 | 主要字段与职责 |
|----|----------------|
| `ticket_setting` | 单行配置：enabled、version、updated_by、updated_at |
| `ticket` | id、ticket_no、author_id、title、category、module、description、steps、expected_result、environment_json、page_path、status、priority、assignee_admin_id、resolution、fixed_version、close_reason、duplicate_of_id、pinned、hidden_at、hidden_by、version、last_activity_at、created_at、updated_at |
| `ticket_message` | ticket_id、actor_type、actor_id、visibility(public/internal)、content、hidden_at、created_at；管理员内部备注也保存于此但必须独立授权查询 |
| `ticket_attachment` | uploader_type、uploader_id、ticket_id、message_id、storage_key、mime_type、size_bytes、width、height、state、created_at、bound_at |
| `ticket_follow` | ticket_id、user_id、created_at，唯一约束(ticket_id,user_id) |
| `ticket_reaction` | ticket_id、user_id、reaction_type、created_at；首版只支持same_issue，唯一约束防重 |
| `ticket_event` | 状态变化、合并、恢复、隐藏等事件，保存操作者、前后状态、公开说明与可见性 |
| `ticket_notification_event` | 如现有设施不足，保存待投递事件和抑制状态，可靠去重和失败重试 |
| 幂等记录 | 优先复用现有机制；没有时新增专用请求幂等记录，绑定用户、动作、请求键、摘要和结果 |

索引与约束：

- `ticket_no` 唯一；工单列表按状态、最后活动时间和 ID 建索引。
- 作者、处理人、分类和模块建立与实际筛选相匹配的索引，不给每个字段盲目建索引。
- 消息按 `(ticket_id, created_at, id)` 分页。
- 临时附件按 `(state, created_at)` 建清理索引。
- 搜索首版支持参数化关键词查询；数据量增长后再评估中文全文检索，不新增外部搜索服务。
- 所有时间存 UTC，客户端按用户时区展示。
- 删除账号后公开记录保留匿名化作者显示“已注销用户”，附件归属关系不能因此变成公开存储地址；和现有账号删除流程一起验收。

## 十、接口建议

具体命名遵循项目现有 `ApiResponse`、身份认证、分页与错误码约定。

### 10.1 用户端

### 10.2 管理端

- 工单设置读取与更新接口，更新限超级管理员。
- 工单列表、详情、公开消息、内部备注和附件接口。
- 管理端公开回复、内部备注分别提供明确动作，避免误发。
- 独立状态变更、处理人分配、优先级、置顶、隐藏与恢复接口。
- 合并和取消合并接口。
- 管理端附件读取不受用户端全局关闭限制，但必须校验管理员权限。
- 所有管理动作写操作日志，隐藏或恢复时必须填写原因。
- 不提供首版工单物理删除接口。

## 十一、安全与稳定性

### 11.1 基础防护

- 工单公开不等于允许任何人修改；用户只能执行被允许的公开互动或作者操作。
- 不允许客户端把普通回复标记为管理员回复或内部备注。
- 普通用户读取隐藏工单返回统一不可用结果，不暴露隐藏内容。
- 内部字段使用独立响应对象，不通过返回数据库整行再让前端隐藏来控制。
- 工单内容按纯文本渲染，SQL 参数化，附件不允许路径穿越或可执行内容。
- 上传请求、工单正文和截图不写入通用访问日志；不需要额外自动隐私扫描。

### 11.2 限流建议

- 新建工单：每用户每分钟最多 2 条、每天最多 20 条。
- 回复：每用户每分钟最多 10 条、每天最多 100 条。
- 图片：每用户每天累计上传最多 200MB，失败上传也要限制请求频率。
- 搜索、关注和“我也遇到”设置合理请求速率，避免反复切换刷接口。
- 超限返回 429 和可重试时间；限流状态不能只保存在单个进程内。
- 数值集中配置，首版不必建设单独的管理界面。

### 11.3 幂等与失败处理

- 创建和回复使用客户端生成的幂等键，重试复用同一键。
- 同用户同动作同键且请求内容相同，返回原结果；内容不同返回冲突。
- 数据库写入与幂等结果保存同事务，至少保留 24 小时。
- 前端按钮提交中禁用；失败保留填写内容，成功后才清空。
- 网络结果不确定时先用幂等请求重试，不让用户重复创建。
- 列表和详情加载失败显示可重试状态，不伪装成空列表。

## 十二、前端交互与适配

### 12.1 用户端

- 大厅采用可扫描列表，不使用大幅宣传页面。
- 状态使用统一标签，管理员回复有身份标记。
- 详情依次呈现原始问题、解决摘要、公开讨论和状态时间线。
- 置顶已知问题和解决办法优先展示，有助于用户提交前找到答案。
- 图片缩略图尺寸稳定，查看大图可以关闭并返回原滚动位置。
- 搜索输入防抖，请求序列保护避免旧结果覆盖新搜索。
- 回复分页，不能一次加载所有历史消息和原图。
- 表单关闭或页面跳转时对未提交内容给出离开确认。
- 全局关闭导致退出时给出明确提示；不继续调用上传或重试写入。
- 不把工单草稿持久化到共享设备的localStorage，首版仅保留当前页面内存。

### 12.2 管理端

- 左侧列表或现有表格布局，详情查看公开内容和内部处理信息。
- 提供待处理、处理中、待补充数量汇总。
- 状态、优先级和处理人使用标准选择控件；开关使用带确认的切换控件。
- 公开回复与内部备注采用明显区分的输入模式，提交按钮标明实际动作。
- 关闭、隐藏、合并均要求原因；合并预览源工单与目标工单后确认。
- 沿用现有主题、图标库和分页组件，避免引入新UI框架。

## 十四、验收场景

### 14.1 公开与权限

- 用户A提交后，用户B可查看正文、图片、公开回复，可标记同问题和回复。
- 用户B不能撤回A的工单、确认解决、修改状态或查看内部备注。
- 未登录、停用账号不能访问工单和图片。
- 普通管理员可处理工单，但不能更改模块开关。
- 管理员隐藏内容后，用户列表、搜索、详情、图片和通知均不可继续读取该内容。

### 14.2 开关

- 默认关闭，用户导航不显示；手工访问路由和API也无法读取。
- 开启后用户无需重新登录即可在配置刷新后看到入口。
- 用户正在填写时关闭，后续提交和上传被拒绝，不产生半条工单。
- 关闭后管理端仍可处理，再开启历史工单和公开回复仍在。
- 通知列表和未读数同步过滤，重新开启不补发关闭期间积压事件。

### 14.3 附件

- 恰好10MiB文件在格式和像素合法时允许上传，超过1字节即拒绝。
- 第6张图片拒绝；伪造扩展名、损坏图片、SVG和超像素图片拒绝。
- 不能关联其他用户临时附件，不能重复绑定附件。
- 临时附件清理不删除已经绑定的图片。
- 上传大小限制在应用和实际反向代理配置中一致有效。

### 14.4 状态与重复工单

- 原作者补充后待补充转为处理中，其他人补充不自动改变状态。
- 管理员标记解决必须有摘要，作者可确认或说明仍未解决。
- 重复工单不能合并自身或形成循环；取消合并保留历史。
- 两名管理员同时变更状态有一方收到冲突提示，不静默覆盖。
- 重复点击“我也遇到”不重复计数，取消后数字正确。

### 14.5 工程验证

- 后端单元/集成测试覆盖权限、开关、状态机、附件、限流、幂等、合并、通知。
- 在真实数据库验证新迁移，不能仅依赖关闭Flyway的预建schema测试。
- 用户端、管理端、桌面端分别执行现有测试、类型检查和构建。
- 375px、390px、768px及桌面视口没有页面整体横向溢出，长标题和图片不挤坏布局。
- 浏览器真实交互覆盖“提交 → 其他用户查看并跟进 → 管理员回复 → 作者确认”。
- 页面无新增控制台错误，分页结果稳定，批量展示避免N+1查询。
