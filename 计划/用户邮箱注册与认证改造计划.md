## 一、最终确认的需求

### 1.1 用户端认证规则

| 场景 | 认证方式 |
|---|---|
| 注册 | 邮箱验证码 + 密码 |
| 登录 | 邮箱 + 密码，或手机号 + 密码 |
| 找回密码 | 邮箱验证码 + 新密码 |
| 登录后修改密码 | 旧密码 + 新密码 |
| 绑定邮箱 | 当前密码 + 新邮箱 + 邮箱验证码 |
| 修改邮箱 | 当前密码 + 新邮箱 + 邮箱验证码 |

### 1.2 管理员规则

管理员保持现状，不参与本次改造：

```text
管理员用户名 + 密码
```

本次不修改：

- `admin_user` 表
- `/api/v1/admin/auth/login`
- 管理员前端登录页
- 管理员 JWT 签发和校验逻辑
- 管理员账号创建和管理流程

### 1.3 明确不支持的方式

- 不新增用户 `username` 字段。
- 不支持用户用户名登录。
- 不把 `nickname` 当作登录名。
- 不把手机号改成邮箱的假地址。
- 不删除现有用户手机号、密码和用户 ID。
- 不通过重新注册新账号迁移日程、团队和提醒数据。

### 3.2 不直接复制的部分

不能原封不动复制 Sub2api 页面，原因包括：

- Sub2api 使用 Tailwind、i18n、Axios 和独立 Pinia store。
- Dayliane 使用自己的 CSS、`apiRequest` 和响应包装格式。
- Sub2api 后端是 Go，Dayliane 后端是 Spring Boot + JDBC。
- Sub2api 找回密码使用邮件链接 token，本项目最终使用邮箱验证码。
- Sub2api 的注册流程会把密码放进 `sessionStorage['register_data']`，本项目不采用明文密码暂存方案。
- Sub2api 的 OAuth、Turnstile、邀请、推广和 2FA 逻辑不属于 Dayliane 本次范围。

### 3.3 采用方式

优先移植以下交互思想，在 Dayliane 现有页面中重新实现：

- 邮箱验证码输入框
- 6 位数字校验
- 发送按钮和 60 秒倒计时
- 重新发送状态
- 密码显示/隐藏
- 字段级错误提示
- 提交中禁用表单
- 成功后跳转和失败后保留输入

## 四、目标用户流程

### 4.1 注册流程

注册表单：

```text
邮箱                 必填
邮箱验证码           必填
密码                 必填
确认密码             必填
手机号               可选
昵称                 可选
时区                 自动读取，可回退 Asia/Shanghai
```

流程：

1. 用户输入邮箱。
2. 前端校验邮箱格式。
3. 用户点击“获取验证码”。
4. 后端创建注册用途的验证码并发送邮件。
5. 用户填写验证码、密码和其他资料。
6. 后端在同一事务中校验验证码、检查邮箱唯一性、检查手机号唯一性并创建用户。
7. 验证码消费成功后，写入 `email_verified_at`。
8. 注册成功后签发用户 access token 和 refresh token。

注册接口不应在只发送验证码时创建半成品用户，避免大量未完成账号污染 `user` 表。验证码挑战暂存于验证码表。

### 4.2 登录流程

登录表单：

```text
邮箱或手机号
密码
```

请求统一使用一个账号字段，例如：

```json
{
  "account": "user@example.com 或 13800138000",
  "password": "Abc12345"
}
```

后端规则：

1. 对 `account` 做 trim。
2. 如果符合邮箱格式，按 `email` 查询。
3. 否则按 `phone` 查询。
4. 两种方式统一使用 BCrypt 密码校验、登录限流和 JWT 签发。
5. 登录失败统一返回，不暴露邮箱或手机号是否存在。

### 4.3 绑定邮箱流程

现有用户可以继续使用手机号和密码登录，然后在个人设置中绑定邮箱。绑定邮箱必须同时验证当前密码和新邮箱验证码：

1. 输入当前密码和新邮箱。
2. 后端验证当前密码，确认当前会话属于该用户。
3. 发送绑定用途的 `bind_email` 验证码。
4. 输入验证码。
5. 后端再次校验当前密码、当前用户 ID、目标邮箱和验证码用途。
6. 检查邮箱未被其他用户占用。
7. 保存邮箱和 `email_verified_at`。

当前密码只在前端内存中短暂保留用于本次操作，不写入 URL、`localStorage` 或 `sessionStorage`。

绑定邮箱不会创建新用户，不改变原有 `user_id`，因此不会影响日程、团队、提醒和通知关联。

### 4.4 修改邮箱流程

修改邮箱需要登录状态，并同时验证当前密码和新邮箱。建议流程：

1. 输入当前密码和新邮箱。
2. 后端验证当前密码，确认当前会话属于该用户。
3. 发送 `change_email` 验证码。
4. 输入验证码。
5. 后端在事务中再次校验当前密码、当前用户 ID、目标邮箱和验证码用途。
6. 检查邮箱唯一性并更新邮箱。
7. 更新 `email_verified_at`。
8. 视安全策略递增 `token_version`，要求其他设备重新登录。

修改邮箱不能复用旧邮箱的验证码，验证码必须绑定用途和目标邮箱。

### 4.5 找回密码流程

未登录用户使用绑定邮箱找回密码：

1. 输入邮箱。
2. 发送 `reset_password` 验证码。
3. 输入验证码、新密码和确认密码。
4. 后端消费验证码并更新密码。
5. 递增 `token_version`。
6. 删除该用户所有 refresh token，使旧会话失效。

无论邮箱是否存在，发送接口都应尽量返回统一结果，降低账号枚举风险。

### 4.6 登录后修改密码流程

保持现有方案：

```text
旧密码 + 新密码 + 确认新密码
```

本次不为普通修改密码增加邮箱验证码。只有忘记旧密码时，才使用找回密码流程。

## 五、数据库改造方案

### 5.1 第一阶段 Flyway 迁移

当前迁移版本为 V19，建议新增 V20，先做增量变更：

```sql
ALTER TABLE `user`
  MODIFY phone VARCHAR(20) NULL,
  ADD COLUMN email VARCHAR(254) NULL,
  ADD COLUMN email_verified_at DATETIME NULL,
  ADD UNIQUE KEY uk_user_email (email);
```

约束说明：

- 新注册用户必须有邮箱。
- 历史用户邮箱可以暂时为空，待绑定后补齐。
- 手机号改为可空，以支持新用户不填写手机号。
- 如果填写手机号，仍必须唯一。
- `password_hash` 继续保留且继续必填。
- `email` 统一 trim、转换为小写后保存。
- 唯一索引默认覆盖软删除记录，保持现有手机号不复用的设计。
- 不删除 `phone`、`password_hash`、`nickname` 或现有用户 ID。

### 5.2 邮箱验证码表

建议新增 `auth_email_otp` 表。字段可按以下设计：

```text
id                  BIGINT 主键
user_id             BIGINT 可空，注册时尚未创建用户
email               VARCHAR(254)
purpose             VARCHAR(32)
code_digest         VARCHAR(255) 或 VARBINARY(64)
status              issued / consumed / expired / invalidated
attempt_count       TINYINT UNSIGNED
max_attempts        TINYINT UNSIGNED
sent_at             DATETIME
expires_at          DATETIME
consumed_at         DATETIME 可空
invalidated_at      DATETIME 可空
request_ip          VARCHAR(45)
user_agent          TEXT
created_at          DATETIME
updated_at          DATETIME
```

`purpose` 至少支持：

```text
register
bind_email
change_email
reset_password
```

建议索引：

```text
(email, purpose, status, expires_at)
(user_id, status)
(expires_at)
```

验证码安全规则：

- 使用安全随机数生成 6 位数字。
- 数据库只保存摘要，不保存明文验证码。
- 默认有效期 5 分钟。
- 同一邮箱 60 秒内不能重复发送。
- 单个验证码最多验证 5 次。
- 重新发送时，旧的 `issued` 记录先置为 `invalidated`。
- 验证成功必须在事务中一次性消费，防止并发重放。
- 过期记录由定时清理任务或定期 SQL 清理。

### 5.3 测试数据库同步

修改生产迁移后，必须同步：

- `src/backend/src/test/resources/schema-test.sql`
- 相关测试的清理表顺序
- 测试中的用户插入 SQL
- 认证安全回归测试

否则测试环境会因缺少 `email`、`email_verified_at` 或验证码表而启动失败。

### 5.4 后续约束收紧

V20 只做增量兼容。完成存量账号邮箱绑定后，再评估是否新增 V21：

- 检查并清理空邮箱。
- 检查邮箱格式和重复数据。
- 根据产品要求将 `email` 收紧为 `NOT NULL`。

不安排删除手机号和密码字段的迁移。手机号仍是用户登录方式，密码仍是登录、注册和修改密码的核心凭证。

## 六、后端接口计划

### 6.1 发送邮箱验证码

建议新增：

```text
POST /api/v1/auth/email-code
```

请求：

```json
{
  "email": "user@example.com",
  "purpose": "register"
}
```

当 `purpose` 为 `bind_email` 或 `change_email` 时，该请求必须携带当前登录用户的身份，并增加当前密码字段：

```json
{
  "email": "new@example.com",
  "purpose": "change_email",
  "currentPassword": "Abc12345"
}
```

注册和找回密码用途不携带 `currentPassword`。绑定/修改邮箱的验证码发送请求应先验证当前密码；最终邮箱提交接口仍必须再次携带并校验当前密码，不能只凭验证码完成邮箱变更。

允许的用途：

```text
register
bind_email
change_email
reset_password
```

响应建议返回：

```json
{
  "countdown": 60
}
```

不返回验证码，不在日志中记录验证码明文。

### 6.2 用户注册

保留路由：

```text
POST /api/v1/auth/register
```

请求建议：

```json
{
  "email": "user@example.com",
  "code": "123456",
  "password": "Abc12345",
  "phone": "13800138000",
  "nickname": "用户",
  "timezone": "Asia/Shanghai"
}
```

后端校验：

- 邮箱格式合法且已验证。
- 验证码用途为 `register`。
- 邮箱未被占用。
- 如果填写手机号，手机号未被占用且格式合法。
- 密码至少 8 位，包含字母和数字，沿用现有规则。
- 昵称和时区沿用现有校验。

### 6.3 用户登录

保留路由：

```text
POST /api/v1/auth/login
```

请求改为：

```json
{
  "account": "邮箱或手机号",
  "password": "Abc12345"
}
```

后端需要新增按邮箱查询用户的逻辑，并把邮箱和手机号登录统一到同一套限流、密码校验和 Token 签发路径。

### 6.4 绑定和修改邮箱

建议新增用户接口：

```text
PUT /api/v1/user/email
```

请求：

```json
{
  "email": "new@example.com",
  "code": "123456",
  "currentPassword": "Abc12345"
}
```

后端从登录 Token 获取当前用户 ID，并检查当前密码、验证码用途、目标邮箱和唯一性后更新。发送绑定/修改邮箱验证码的请求也必须处于登录状态并先验证当前密码；最终提交时再次验证当前密码，避免验证码挑战在密码变更后仍可被使用。

### 6.5 找回密码

发送验证码复用：

```text
POST /api/v1/auth/email-code
```

用途为：

```text
reset_password
```

新增或改造重置接口：

```text
POST /api/v1/auth/reset-password
```

请求：

```json
{
  "email": "user@example.com",
  "code": "123456",
  "newPassword": "NewAbc12345"
}
```

重置成功后必须递增 `token_version` 并清理 refresh token。

### 6.6 登录后修改密码

保留现有接口：

```text
PUT /api/v1/user/password
```

请求仍为：

```json
{
  "oldPassword": "Abc12345",
  "newPassword": "NewAbc12345"
}
```

后端继续：

- 校验旧密码 BCrypt 哈希。
- 校验新密码强度。
- 更新 `password_hash`。
- 递增 `token_version`。
- 清理当前用户 refresh token。

## 七、腾讯云邮件服务接入计划

邮件服务需要做成后端配置，不把密钥写入代码、Git 或数据库业务表。

### 7.1 配置项建议

后端环境变量建议预留：

```env
TENCENT_SES_ENABLED=false
TENCENT_SES_REGION=
TENCENT_SES_SECRET_ID=
TENCENT_SES_SECRET_KEY=
TENCENT_SES_FROM_EMAIL=
TENCENT_SES_TEMPLATE_ID=
TENCENT_SES_REPLY_TO=
```

实际采用腾讯云 API 还是 SMTP，需要根据用户提供的腾讯云账号能力最终确定。邮件发送服务应抽象为接口，验证码业务不直接依赖具体供应商。

### 7.2 发信配置要求

上线前需要准备：

- 已验证的发信域名。
- 已验证的发信地址，例如 `noreply@...`。
- 邮箱验证码模板。
- 注册、绑定邮箱和找回密码的邮件文案。
- 发送地域。
- 专用的最小权限访问凭证。
- 测试收件邮箱。

邮件正文至少包含：

```text
验证码
有效期
用途说明
请勿向他人泄露
```

### 7.3 凭证安全

- 不在聊天中提交完整 `SecretKey`。
- 不在前端暴露邮件服务密钥。
- 不把验证码写入访问日志、异常日志或数据库明文列。
- 生产环境只使用环境变量或密钥管理服务。
- 开发环境可以使用测试发件地址和测试邮箱，不能使用生产密钥提交到仓库。

流程可以设计为同页两步：

1. 输入邮箱并发送验证码。
2. 输入验证码、新密码和确认密码。

不采用 Sub2api 的邮件链接 token 页面，不把密码写入 `sessionStorage`。

### 8.3 个人设置页面

主要改造：

- `src/web-user/src/views/ProfileSettingsPage.vue`
- `src/backend/src/main/java/com/dayliane/user/UserController.java`
- `src/backend/src/main/java/com/dayliane/user/UserService.java`

增加：

- 当前邮箱展示。
- 邮箱是否已验证。
- 绑定邮箱：当前密码 + 新邮箱 + 验证码。
- 修改邮箱：当前密码 + 新邮箱 + 验证码。

绑定或修改邮箱时，当前密码只保存在组件内存中，操作结束、失败或离开页面后立即清除，不写入浏览器持久化存储。

密码区域保持：

```text

新密码
确认新密码
```

不增加修改密码邮箱验证码。

```json
  "emailVerifiedAt": "..."
}
```

手机号仍继续返回，团队成员页面和管理员用户列表可以继续展示手机号。

## 九、安全设计

### 9.1 验证码安全

- 服务器使用安全随机数生成验证码。
- 数据库保存摘要，不保存明文。
- 验证码只允许消费一次。
- 验证码必须绑定邮箱、用途和有效期。
- 错误次数达到上限后作废。
- 重发验证码时作废旧验证码。
- 验证码不得出现在响应、日志、异常消息和前端 URL 中。

### 9.2 限流

至少实现以下限制：

- 同一邮箱 60 秒内不能重复发送。
- 同一 IP 的发送频率限制。
- 同一邮箱每日发送数量限制。
- 单个验证码验证失败次数限制。
- 登录仍沿用现有 IP 和账号限流。

当前 `LoginRateLimiter` 是单机内存实现。若未来部署多实例，应把验证码和发送限流迁移到 Redis、数据库或网关层，不能依赖单个 JVM 内存。

### 9.3 账号枚举防护

- 找回密码发送接口对“邮箱存在”和“邮箱不存在”尽量返回相同结果。
- 登录失败统一返回“账号或密码错误”。
- 注册冲突可以返回明确的业务冲突，但不返回数据库异常。
- 邮箱唯一冲突统一映射为稳定的业务错误码。

### 9.4 会话失效

以下操作成功后必须使旧会话失效：

- 找回密码。
- 修改邮箱时的安全策略变更。
- 登录后修改密码。
- 管理员停用用户时的现有状态检查继续生效。

用户的 `token_version` 和 refresh token 机制优先复用，不新增第二套会话系统。

## 十、存量用户迁移

### 10.1 迁移原则

- 不创建新账号替代旧账号。
- 不改变现有 `user_id`。

2. 部署支持邮箱字段和绑定接口的后端。

8. 使用邮箱和密码重新登录。

## 十二、测试计划

### 12.1 后端单元和集成测试

验证码：

- 正确验证码可以验证。
- 错误验证码被拒绝。
- 过期验证码被拒绝。
- 验证码只能消费一次。
- 超过最大尝试次数后作废。
- 重发后旧验证码失效。
- 发送冷却时间生效。
- 不同用途的验证码不能混用。

注册：

- 邮箱验证码正确时可以注册。
- 未提供验证码时不能注册。
- 邮箱重复时返回稳定冲突错误。
- 手机号为空时可以注册。
- 手机号重复时不能注册。
- 注册后邮箱验证时间已写入。
- 注册后可以正常签发 access token 和 refresh token。

登录：

- 邮箱 + 密码登录成功。
- 手机号 + 密码登录成功。
- 错误密码失败。
- 未验证邮箱的历史账号仍可手机号登录。
- 登录限流仍然生效。

邮箱管理：

- 登录用户必须提供当前密码才能绑定邮箱。
- 绑定重复邮箱失败。
- 修改邮箱必须提供当前密码和新邮箱验证码。
- 绑定邮箱必须提供当前密码和新邮箱验证码。
- 旧邮箱和新邮箱不能混用验证码。
- 密码错误时不能发送或消费绑定/修改邮箱验证码。

密码：

- 找回密码验证码正确时可以设置新密码。
- 找回密码成功后旧 refresh token 失效。
- 登录后修改密码仍要求旧密码。
- 修改密码成功后旧 refresh token 失效。
- 新密码可以登录，旧密码不能登录。

### 12.2 前端测试

- 邮箱格式校验。
- 手机号格式校验。
- 验证码只能输入 6 位数字。
- 发送后按钮进入倒计时。
- 倒计时结束后可以重新发送。
- 表单提交期间按钮禁用。
- 注册错误不会清空无关字段。
- 找回密码页面的验证码和密码确认状态正确。
- 个人设置绑定/修改邮箱时显示当前密码、新邮箱和验证码字段。
- 绑定/修改邮箱过程中不把当前密码写入 `localStorage` 或 `sessionStorage`。
- 修改密码仍显示旧密码输入框。
- 不把密码写入 `sessionStorage`。

## 十三、回滚方案

### 13.1 应用回滚

如果邮件发送、验证码或新注册流程出现问题：

1. 关闭新注册邮箱验证功能开关。
2. 保留旧手机号密码登录。
3. 回滚前端到上一版本。
4. 保留新增邮箱列和验证码表，避免破坏已经绑定的数据。

### 13.2 数据库回滚

- 优先回滚应用版本，不主动删除 V20 新增字段和表。
- 不回滚已经消费的验证码记录。
- 不立即删除 `email`、`email_verified_at` 或 OTP 表。
- 只有确认没有任何新数据写入并完成备份后，才评估结构回滚。
- 禁止使用会删除生产数据卷的回滚方式。

### 13.3 不可逆操作

第一阶段不执行以下操作：

- 删除 `phone`。
- 删除 `password_hash`。
- 删除用户旧登录接口。
- 删除用户账号。
- 合并用户记录。
- 重建用户 ID。
